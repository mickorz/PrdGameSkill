# Game PRD Check Skill

读取 `input/` 下的原始 PRD 需求文档，对照 `references/rules/` 下的检查规范（规则基准，视为正确答案），按七阶段流水线生成结构化问题报告。本流程与 `.opencode-workflows/workflows/game-prd-check.js` 同源，逻辑保持同步。

## 参数（均可按需覆盖）

| 参数 | 默认值 | 说明 |
|---|---|---|
| inputDir | `input` | 需求文档目录 |
| inputFiles | 扫描 inputDir 得到 | 指定需求文档路径数组（给定时跳过扫描） |
| rulesDir | `references/rules` | 规则基准目录 |
| templatePath | `references/templates/report.template.md` | 报告模板 |
| outPath | `examples/game-prd-check-workflow/report.md` | 报告输出路径（固定，不要改） |
| date | 当天（系统时间，YYYY-MM-DD） | 检查日期 |
| maxIssuesPerGroup | 10 | 每组最多报告的问题数 |
| excludeKeywords | `["金币场"]` | 本期不检查的主题关键词，命中 module/title/location/ruleRef 即剔除 |
| fast | false | 最快档：规则组压到 16 组以内、确定性去重、报告分片并行写、默认跳过质检 |
| skipReview | false（fast 档默认 true） | 跳过报告质检阶段 |

## 执行流程（七阶段）

### 阶段 1：扫描

只做清单扫描，不读正文判断：

1. 列出 `inputDir` 下所有 Markdown 需求文档（相对仓库根路径）。
2. 把 `rulesDir` 下规则文件按主题分组：
   - 小文件（≤20KB，约 8000 字）按业务流程阶段合并成组（如 开局与发牌 / 摸打吃碰杠 / 结算与分数 / 配置与做牌 / 重连 / 广播与数据）；总览、目录、索引类文件放第一组。
   - 单文件超过 20KB 时按一级章节拆分：一章一个片段一组，记录 `{ file, fromLine, toLine, title }`，片段必须首尾相接覆盖全文（用 grep 查章节标题、read 带 offset 确认行号）。
   - 每组给出 `title`（组名）、`focus`（一句话说明管什么）、`files`（完整路径）或 `sections`（行范围片段）。
   - 总组数上限：fast 档 16 组，否则 24 组；超上限时相邻章节合并进同组，不得漏内容。
   - 规则目录结构与说明不同时自适应分组，仍要覆盖全部规则文件。

### 阶段 2：规则检查（并行）

每组派一个只读子代理并行执行（建议并发 16 路，子代理失败重试 1 次），子代理任务要点：

- 读全部需求文档（全文逐段读完，大文件分段读）。
- 把本组每条规则与需求文档逐条对照，只报本组范围内的问题（其他组的问题不报）。
- 规则文件是基准；只报需求文档的缺失、冲突、逻辑错误、模糊与不完整。
- 每条问题输出为下方「问题字段」结构化 JSON，最多 `maxIssuesPerGroup` 条，按优先级从高到低挑选最有价值的。

### 阶段 3：一致性检查（与阶段 2 并行）

另派一个子代理只做需求文档内部检查，不按规则清单对照：

- CONFLICT：文档内部两处描述互相矛盾。
- AMBIGUOUS：同一处描述可多种理解。
- INCOMPLETE：流程、状态、数值、异常分支缺失。
- 不报规则基准里有但文档没写的内容（那属于阶段 2 的规则覆盖检查）。

### 阶段 4：汇总去重

1. 合并阶段 2 各组结果与阶段 3 结果；个别分组失败只影响覆盖说明，不中断流程。
2. 按 `excludeKeywords` 剔除不检查主题（命中的不计入统计），记录剔除条数。
3. 去重：
   - 问题总数 > 15 且非 fast 档：把问题索引（i/type/priority/title/location）交给一个归并代理，找出同根因重复组；重复项不删除，主条目标注「（与 PRD-xxx 同根因，重复登记，建议合并）」，重复条目的 location 并入主条目。
   - 否则（fast 档或问题较少）：确定性去重——同 `type + location + 标题前 12 字`（去空白标点小写后比较）视为同一条，登记为同根因。
4. 排序编号：优先级 P0→P3，同级按类型 MISSING→CONFLICT→LOGIC→AMBIGUOUS→INCOMPLETE；确定编号 `PRD-001` 起连续编号，统计各优先级/类型/模块数量（统计只做内部用，报告以主题分布呈现）。

### 阶段 5：主题归类

把问题归入可读的业务主题（替代 MISSING 等抽象检查类型）：

1. 主题是「业务对象 + 问题性质」短语，4~12 字（如 三摊承包口径冲突、断线重连缺失、超时兜底缺失）。
2. 禁止英文检查类型词，禁止「文档规范要素缺失」这类抽象主题。
3. 同一缺陷簇必须用完全相同的主题写法；每条问题只归一个主题。
4. 同根因标注条目必须与主条目同主题。
5. 主题数量 8~25 个；覆盖全部问题，不能遗漏重复。
6. 归类失败的问题用其 module 兜底。

### 阶段 6：生成报告

按 `templatePath` 四段结构写入 `outPath`（唯一交付物）：

- **头部**：检查对象、检查范围（排除关键词时写明）、规则基准、检查日期。
- **1 检查概览**：统计表（总数/P0/P1/P2/P3）+ 主题分布表。统计数字原样使用，不得自行改数。
- **2 问题清单**：表格 `ID | 主题 | 问题性质 | 优先级 | 问题 | 原文位置 | 建议`，列出全部条目一条不漏，顺序与编号一致；主题列不得出现英文检查类型；问题性质列逐条必填五类型中文名（需求缺失/内容冲突/逻辑错误/定义歧义/描述不完整），无详情块的长尾条目也必须给出，有详情块的与详情块问题性质一致；建议列取精简版。
- **3 重点问题详情**：展开全部 P0/P1 + 最多 3 条典型 P2。每条固定顺序：优先级、主题、问题性质（类型的中文名，与问题清单表的问题性质列一致）、术语解释（term_explain 非「无」才写）、原文（`**原文**（位置）：`+ 引文）、问题、影响、需要补的内容与必填格式（required_format 非「无」才写）、范例（example 非「无」才原样保留，保证可照抄）、建议、验收口径（acceptance）、处理状态（默认 待确认）。为「无」或空的小节跳过，不得编造；引文必须来自 quote 字段。
- **4 总体建议**：问题最多的主题（取主题分布第一名，附 ID 列表）、可能影响开发的问题（列 P0/P1 的 ID）、是否建议进入下一阶段（存在 P0 或 P1 较多则暂缓，否则建议）+ 理由。

fast 档可把报告拆成「概览+清单」「详情+建议」两个分片并行写后合并；默认档单代理整篇写。报告中不使用 Emoji，UTF-8。

### 阶段 7：报告审核（skipReview 时跳过）

派一个质检代理按模板审核，逐项检查：

1. 四段结构完整、标题与模板一致。
2. 头部信息已填写（无占位符）。
3. 概览统计与期望总数/优先级分布一致。
4. 清单行数 = 期望总数，ID 连续无跳号。
5. 清单表头正确，主题列为具体业务主题（无英文类型词），问题性质列为五类型中文名且逐行无缺失、与详情块一致，优先级只四级。
6. 详情条目含主题与中文问题性质、有原文引文、条数不少于期望；专有术语有解释；缺章节/缺表类有必填列与可照抄范例。
7. 无编造内容（引文与清单对不上、凭空新增问题）。

不通过则派修正代理只按质检意见修改（事实与统计不变，不得增删条目，以清单 JSON 为准），修正后确认 `outPath` 存在。

### 阶段 8（可选）：生成 Dashboard

运行 `node scripts/build-dashboard.mjs <outPath>`，解析 report.md 生成 `report.json` 与离线单文件 Dashboard（文件名 `{项目名}分析-Dashboard-{YYYYMMDD}-{序号}.html`，同日递增不覆盖；产物目录已 gitignore 本地保留）。校验失败（`[失败]` 输出）时先修 report.md 再重跑。设计见 `dev-docs/design/PRD-Quality-Dashboard-Design-v1.0.md`。

## 问题字段（每条问题的结构化定义）

| 字段 | 说明 |
|---|---|
| type | 五类之一：MISSING / CONFLICT / LOGIC / AMBIGUOUS / INCOMPLETE |
| priority | 四级之一：P0 / P1 / P2 / P3 |
| title | 一句话问题，不超过 40 字 |
| module | 所属模块或章节主题（如 发牌 / 结算 / 重连） |
| location | 需求文档原文位置（章节/小节标题），多处用、分隔 |
| quote | 原文引文，不超过 200 字；MISSING 类写缺失说明 |
| ruleRef | 对应规则文件与规则点（相对路径 + 章节或条目） |
| problem | 问题说明，指出违反哪条基准或哪里矛盾；涉及术语先用 term_explain 的定义表述 |
| impact | 对开发 / 测试 / 验收的具体影响 |
| suggestion | 具体可执行的补充或修正建议 |
| term_explain | 专有名词解释，「术语＝一句话定义」；无则填「无」 |
| required_format | 修复必须采用的格式（必填列或章节结构）；非格式类填「无」 |
| example | 可直接照抄的完整示例，正常与异常各一条；非格式类填「无」 |
| acceptance | 补齐后的验收口径：怎样算达标、测试能否直接出用例 |

类型中文映射（报告用）：MISSING=需求缺失、CONFLICT=内容冲突、LOGIC=逻辑错误、AMBIGUOUS=定义歧义、INCOMPLETE=描述不完整。

## 检查硬性要求（12 条，子代理提示词必须包含）

1. 证据先行：每条问题给出原文位置与引文，禁止无依据推测。
2. 以 rules 为准：需求文档与 rules 冲突时，记问题的是需求文档，不质疑规则本身。
3. 报前复核：报 MISSING/LOGIC 前先回规则基准确认没有相反要求；规则没要求的不得当问题（如规则写明「只记录数据不常驻显示」，就不能报「缺少局内展示」）。
4. 不臆造：确实没写才算 MISSING；写了但含糊才是 AMBIGUOUS/INCOMPLETE。
5. 不重复：同一问题只记一条，多处证据合并写进同一条的 location。
6. 术语先解释：标题或问题含专有名词/缩写/自造词（跨层通知、进张、幂等、原版/修改对比版、无表、口径等）时，term_explain 写定义，problem 首句用解释后的说法。
7. 缺失类必须给格式：缺章节/缺表/格式不清时，required_format 写必填列或章节结构；example 给正常与异常各一条可照抄的完整示例（真实内容，禁止 {占位符}，示例数值注明「示例值以产品确认为准」）。
8. 冲突类必须定位：写明两版分别在哪节哪表、逐点列差异；建议给「生效声明」写法与版本差异对照表。
9. 每条都写 acceptance：补齐后如何判定合格，测试能否直接转用例。
10. 只报本范围规则能支撑的问题，不越界检查别的模块。
11. 按优先级从高到低自检，最多输出 `maxIssuesPerGroup` 条最有价值的。
12. 只输出结构化结果，不输出报告正文。

## 优先级定义

| 优先级 | 判定标准 |
|---|---|
| P0 | 关键流程/规则缺失或矛盾，直接阻塞开发或验收 |
| P1 | 明确的冲突、逻辑错误，不解决会导致实现错误 |
| P2 | 模糊、不完整，需要澄清后才能实现 |
| P3 | 优化建议，不影响正确性，但补充后文档质量更高 |

## 输出位置

- 报告：`examples/game-prd-check-workflow/report.md`（唯一交付物，固定不要改）
- Dashboard（可选）：同目录 `report.json` 与 `dashboard/{项目名}分析-Dashboard-{YYYYMMDD}-{序号}.html`（产物目录已 gitignore，本地保留版本对比）
