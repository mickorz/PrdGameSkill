# 游戏核心流程模板——双版本补全

以核心流程模板为基础，对照创房规则文件与玩法模块客户端代码，补全头部（玩法选项规则全集 + 名词）与正文流程（缺口补充），一次产出两份文档：

- **程序补全版**：完整规则 + 规则字段名、协议/类/枚举名、gameId、`文件:行号` 锚点 + 附录（锚点索引 / 逐章核对表 / 待确认清单）——给程序与服务端对接用。
- **策划补齐版**：同一份规则的策划投影——剔除全部程序信息，只留选项规则、显隐联动、行为与流程描述、待确认问题——给策划/产品用。

两版正文（开局→结算）都逐字保留基础模板原文；补全内容只在头部选项、名词补充、流程补充、待确认四处展开。

## 输入

| 参数 | 默认 | 说明 |
|---|---|---|
| templatePath | templates/ 下的核心流程基础模板（如「…AI-核心简化版本.md」） | 待补全的基础模板 |
| codeMapHead | `references/hzmj-code-map.md` | 头部锚点图（创房规则 + 名词术语源） |
| codeMapFlow | `references/hzmj-flow-code-map.md` | 正文锚点图（协议/数据/控制器/视图） |
| outDevPath | `templates/{模板名去「-核心简化版本」}-核心程序补全版.md` | 程序版产物 |
| outDesPath | `templates/{模板名去「-核心简化版本」}-核心策划补齐版.md` | 策划版产物 |

## 执行流程

1. **选基读码**：读基础模板与两份锚点图。编码坑：客户端目录混有 UTF-8/GBK，先跑 `node .claude/skills/game-prd-complete/scripts/normalize-gbk.mjs <file>` 探测，乱码文件读它输出的 UTF-8 副本。
2. **头部补全（规则不固定）**：按 codeMapHead 提取创房选项规则全集（单选/人数联动/复选组/通用规则/创房不可见默认/已停用与兄弟玩法）——开篇总述改写为全配置总述（人数、局数/打片模式、全部可选值与客户端默认值），**不写「本期固定」、不标 ★**；选项表以「客户端默认」为基准列，全部可选值+默认值+人数联动列全。正文流程按客户端默认配置展开，并在程序版头部说明中注明该基准；**策划版不设说明引注**（「## 玩法选项」章头后直接跟选项表）。
3. **正文核对补全**：按 codeMapFlow 逐章核对，四类结论——已覆盖（附锚点）/ 服务端裁决（客户端不可证，标注）/ 缺口（代码有、模板没写 → 补充）/ 不适用（登记不补）；死代码（无消费方）不算缺口。
4. **双版本落盘**：
   - **名词并入原列表**：补充词条直接并入「## 名词」原列表——原词条在前、新词条按原列表风格追加其后；**不设「### 补充名词」小节**。原词条中「本期固定 X」类配置措辞做**去固定化改写**（牢庄→全档位+庄闲倍数、财神→白板财神/翻财神双模式），其余逐字保留。程序版新词条带锚点（纯代码别名词条如「荒牌」仅程序版保留），并在「## 名词」下加一行引注；策划版纯语义、不加注。
   - **流程插进对应章节**：缺口流程直接补进所属正文章节——新小节或新条目插在该流程发生的位置（如断线重连→「行牌」章末新小节、听牌分级与简洁模式→「出牌与响应」内新条目）；**不设独立「流程补充」章**。
   - 程序版 = 头部补全（含字段列与锚点）+ 名词并入（带锚点）+ 正文（含插入流程，带锚点）+ 附录 A（锚点索引）/ B（头部待确认）/ C（逐章核对结论 + 登记不适用 + 锚点索引 + 流程待确认）。
   - 策划版 = 头部补全（剔除字段列与全部锚点，联动描述改用选项名表述）+ 名词并入（纯语义）+ 正文（含插入流程，纯行为描述）+ 文末「登记不适用」简表 + 待确认清单（无锚点的产品问题）；不设附录。
5. **验收**（脚本比对）：
   - 头部（开篇+选项+名词）无「本期固定」字样与「★」标记；开篇含全配置总述（全部可选值+默认值）；
   - 名词节为单一列表：无「### 补充名词」小节，未去固定化的原词条逐字保留；
   - 全文无「## 流程补充」章；插入点之外，正文与基础模板逐字一致（按插入点分段比对）；
   - 策划版扫描无程序标记（见剔除清单）；
   - 程序版每条补全条目带 `文件简写:行号` 锚点，待确认编号全局连续（B:1-N，C 接续 N+1-M；策划版 1-M）；
   - 两版一致性：策划版每条规则都能在程序版找到对应表述。

## 策划版剔除清单（硬规则）

策划版不得出现：

- 代码文件名（`*.ts` 等）与 `文件:行号` 锚点；
- 规则字段名（snake_case，如 simple_mode、ui_play_count）；
- 协议/类/枚举/常量名（MsgPower、GameData、HzmjFanType、K_FTG_* 等）；
- gameId 数字（42319/42320/…）；
- 「锚点 / 协议 / 字段 / 枚举 / gameId」等术语与内部技能、工具引用；
- 逐章核对表、锚点索引等程序侧过程信息。

保留：选项名、档位值（如 40/50/60 片）、默认值、显隐联动规则、行为与流程描述、番型与结算规则、待确认问题。

## 硬规则

- 证据先行：程序版每个结论与条目附 `文件简写:行号` 锚点；禁止凭空推测。
- 只读代码：不修改任何客户端代码。
- 原文不动：基础模板正文（开局→结算）逐字保留；补充只以同列表追加、章节内插入方式落地，不另设补充章。开篇三段与名词原词条中的「本期固定」类配置措辞做去固定化改写（改为全档位/双模式表述），其余逐字保留。
- 服务端裁决项不得写成「已验证」：客户端代码只证明展示与拦截，不证明仲裁规则；程序版标注并引服务端规则基准佐证，策划版转为待确认问题。
- 跨玩法隔离：萧山（跟庄骰子）、金币场（加倍、好运来运营曝光）、二人场变体不得混入好友房正文。
- UI 表现细节归 `ui-interaction-prd-extract` 基准：程序版引用处注明分工；策划版不引用内部技能。
- 策划版是程序版的投影，不得引入程序版没有的规则或结论。

## 与其他技能关系

- 本技能由 game-prd-head-complete（头部）与 game-prd-flow-complete（正文）合并而来，一次执行产出双版本。
- `ui-interaction-prd-extract`：UI 交互表现层基准（按钮布局、倒计时、动效）。
- `game-prd-check`：双版本文档可作它的检查输入；其服务端规则基准（`references/rules/hzmj_game_flow_handler/`）可佐证程序版的「服务端裁决」项。
