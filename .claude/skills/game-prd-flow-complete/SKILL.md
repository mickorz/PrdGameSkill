# 游戏核心流程模板——正文流程补全

对照玩法模块客户端代码，核对核心流程模板的正文各章（开局/行牌/三摊承包/算分/番型/结算），找出**代码里有、模板没写**的流程并补充，标注客户端不可证（服务端裁决）与不适用项。头部（玩法选项+名词）归 `game-prd-head-complete`，本技能只管正文流程。

## 输入

| 参数 | 默认 | 说明 |
|---|---|---|
| templatePath | templates/ 下最新工作版：有「-头部补齐」版用之，否则「-核心简化版本」原版 | 待补全的核心流程模板 |
| codeMapPath | 本技能 `references/hzmj-flow-code-map.md` | 流程代码锚点图（协议/数据/控制器/视图分层） |
| outPath | `templates/{基名去「-头部补齐」}-流程补齐.md` | 产物路径，与基文档同目录 |

## 执行流程

1. **选基读码**：确定基文档（头部补齐版优先），按锚点图读代码。编码坑：客户端目录混有 UTF-8/GBK，先跑 `node .claude/skills/game-prd-head-complete/scripts/normalize-gbk.mjs <file>` 探测，乱码文件读它输出的 UTF-8 副本。
2. **读协议主干**：`protocol/GameGlcProtocol.ts` 的 GAME_STATUS 状态机 + 消息类清单（S→C/C→S/已注释三栏）是流程骨架；再读 `data/GameData.ts` 关键簇与 `controller/gameController.ts` 的协议处理。
3. **逐章核对**：模板正文每章 vs 代码事实，给四类结论：
   - **已覆盖**：模板描述与代码一致（附锚点）；
   - **缺口**：代码有流程、模板没写 → 补充（如断线重连恢复、听牌提示分级）；
   - **服务端裁决**：客户端只收结果不做裁决（如操作优先级仲裁、禁张算法）→ 标注「客户端不可证」，可引 `game-prd-check` 的服务端规则基准佐证（`game-prd-check/references/rules/hzmj_game_flow_handler/`）；
   - **不适用**：代码存在但本期固定/本玩法/场景不启用（金币场加倍、萧山跟庄、做牌、复盘、补花、托管、死代码）→ 登记不补充。
4. **补充落盘**：产物 = 基文档全文 + 新章节「## 流程补充（代码检索）」（插在最后一个流程章节之后、附录之前）：逐章核对结论表 + 每个缺口流程一小节（带锚点）+ 登记不适用表；文末追加「附录 C：流程核对与待确认」。基文档原文（含头部补齐与附录 A/B）一个字不动。
5. **验收**：脚本比对产物与基文档——基文档内容必须逐字包含于产物；补充条目每条都有 `文件简写:行号` 锚点；待确认清单编号接续基文档既有编号。

## 硬规则

- 证据先行：每个核对结论与补充条目都附 `文件简写:行号` 锚点；禁止凭空推测。
- 只读代码：不修改任何客户端代码。
- 原文不动：基文档全部内容逐字保留；补充只以新章节/新附录形式追加。
- 服务端裁决项不得写成「已验证」：客户端代码只能证明展示与拦截，不能证明仲裁规则；引用服务端规则基准时要注明出处。
- 跨玩法隔离：萧山（跟庄骰子）、金币场（加倍、好运来运营曝光）、二人场变体不得混入好友房正文流程。
- 死代码不算缺口：数据结构/事件名存在但全模块无消费方（如杠分），登记为预留/死代码。
- UI 表现细节（按钮布局、动效、字效）归 `ui-interaction-prd-extract` 基准，本技能只补「流程」本身；引用处注明分工。

## 与其他技能关系

- 承接 `game-prd-head-complete`：头部（玩法选项规则全集+名词）由它补全，本技能在其产物上继续补正文。
- `ui-interaction-prd-extract`：UI 交互表现层基准；本技能流程核对涉 UI 时引它，不重复展开。
- `game-prd-check`：本技能产物（流程补齐版）可作它的检查输入；其服务端规则基准可反向佐证本技能的「服务端裁决」项。
