# Game PRD Head Complete Skill

给定一份游戏核心流程模板（如 `templates/【杭州麻将】核心流程杭州麻将好友房AI-核心简化版本.md`），检索客户端代码中的创房规则文件与玩法定义文件，把模板头部两部分补齐：

1. **玩法选项规则全集**：模板开篇摘要只写了本期固定值（四人好友房、固定 8 局等）；补全为完整选项空间——每个选项的规则字段、可选值（desc=value）、客户端默认值、显隐联动、本期固定值（★）标注。
2. **名词补齐**：对照代码术语源（选项名、番型枚举、HuType/EndType/CombType 等）检查模板「名词」小节，补充缺失术语，每条带代码锚点；已有名词保留原文，代码口径冲突（如 流局 vs EndType「荒牌」）只加「代码别名」注记。

正文其余章节（开局/行牌/算分/结算等）一律不动。

## 输入与输出

| 项 | 默认值 | 说明 |
|---|---|---|
| templatePath | `templates/【杭州麻将】核心流程杭州麻将好友房AI-核心简化版本.md` | 待补齐的模板 |
| game | 从模板文件名/内容识别（当前实例：杭州麻将好友房，gameId 42320） | 决定用哪张代码锚点图 |
| codeMapPath | `references/{game-slug}-code-map.md`（当前：`references/hzmj-code-map.md`） | 客户端代码锚点图 |
| outPath | `templates/{模板名去扩展名}-头部补齐.md` | 产物固定写入 `templates/`，重跑覆盖 |
| inPlace | false | 用户明确要求时才直接改模板原文件 |

产物结构：模板全文 + 头部两部分补齐 + 文末两个附录——「代码锚点索引」（锚点简写 → 完整路径）与「待确认清单」（术语映射不上规则字段、或本期固定值与客户端默认不同的项）。

## 执行流程（五步）

### 第 1 步：定位与读取代码

1. 读模板全文，识别游戏与玩法变体（文件名、正文玩法名 → gameSlug、gameId）。
2. 按代码锚点图读主规则文件；锚点图路径失配时按图内「路径漂移兜底搜索」重新定位，找到后回写锚点图。
3. **编码坑**：客户端代码目录混有 UTF-8 与 GBK 文件。用 Read 读到中文乱码（如「妯″紡」样式）时，先执行 `node .claude/skills/game-prd-head-complete/scripts/normalize-gbk.mjs <文件...>` 检测并生成 UTF-8 副本，读副本；禁止基于乱码内容提取事实。

### 第 2 步：提取选项规则

从规则文件提取（每条带行号锚点）：

- `DefaultConfig{玩法}`：与服务端 game_rule 对齐的默认参数，含创房 UI 没有的隐藏字段（play_count/play_score 派生与互斥、首局庄家、轮庄、流局连庄、play_speed 等）。
- `BoxRoomGameRuleButtonConfig{玩法}.gameRule`：创房面板全部选项——每栏 title、items（desc/value）、default（Radio 是 items 下标；Checkbox 组是数组，按位对应 items）、显隐联动。联动语义以实现代码为准（见锚点图「联动语义」节）：
  - `relatedInitRule {ruleName, value/values}`：本栏/本单项仅当规则 ruleName 的值为 value/values 之一时显示。
  - `relatedRadioRule {ruleName, value: 0|1, SHOW, index: V}`：选中本项后，目标组中 value=V 的单项隐藏(0)/显示(1)。
  - `relatedRadioRule {ruleName, value: 0|1, SHOW}`（无 index）：选中本项后，目标组整组隐藏(0)/显示(1)。
  - `relatedRadioRule {ruleName, value: X, SELECTED}`：选中本项后，目标组中 value=X 的单项被选中且规则值写为 X。
  - `relatedCheckboxRule {ruleName, value: 0|1, SHOW}`：选中本项后，目标复选框隐藏(0)/显示(1)。
- 通用规则 `CommonRule` + `CommonRuleConfig`（可托管/托管解散/超时解散/自动准备/截屏监控等，含默认勾选态）。
- 已注释停用的选项（整段注释代码）单独列出并标注「已停用」。
- 同族兄弟玩法的配置（如二人版 `DefaultConfigERHZMJ`、分支文件 `HzmjRuleShared.ts` 服务淳安/萧山/桐庐）只登记存在与差异要点，不进本玩法选项全集。

### 第 3 步：核对本期固定摘要

把模板开篇摘要逐项映射到规则字段（示例：固定 8 局 → ui_play_count=8 → play_count=8；白板财神 → cai_shen_type=0；笃三老庄 → banker_level_type=2；无托管 → CommonRule.BOT 未勾选）：

- 映射得上且与客户端默认一致 → 选项表标「★本期固定」。
- 映射得上但与客户端默认不同 → 标「★本期固定（客户端默认 X，与本期不同）」并进待确认清单。
- 摘要术语映射不上任何规则字段（如「吃碰禁手」vs rule_chi_peng 三档）→ 进待确认清单，给出最接近候选与代码依据，禁止替用户拍板。

### 第 4 步：改写头部第一部分

在 `# 核心需求` 与 `## 名词` 之间插入「## 玩法选项（客户端创房规则全集）」小节：

- 开篇摘要三段原样保留（已核对），后接：
- 单选项表：选项标题 / 规则字段 / 可选值（desc=value）/ 客户端默认 / 本期固定 / 显隐联动 / 锚点。
- 复选规则组表：勾选项 / 规则字段 / 客户端默认 / 本期固定 / 显示条件 / 锚点。
- 通用规则表、隐藏字段表（无 UI 的服务端字段）、已停用选项与兄弟玩法登记。
- 锚点写 `文件简写:起-止行`；文件简写 → 完整路径集中在文末「代码锚点索引」。

### 第 5 步：名词补齐与落盘

1. 对照锚点图「名词术语源」节逐项过：创房选项名（打片、翻财神、笃二老庄、平庄起、两摊封顶、碰算摊、有财必拷响、三财翻倍、四财翻倍、十风牌、无风牌、缺一色、财神替豪七、守庄、连庄不占局数等）、番型枚举名、HuType/EndType/CombType/ActionAniType 枚举注释。
2. 只补与本玩法相关的术语；其他玩法的术语（如 FanDefine 中萧山番型 K_FTG_XSMJ_*）不得混入。
3. 已有名词保留原文；冲突只加「代码别名」注记。
4. 新词条一句定义 + 锚点；代码里只有选项名没有语义展开的，定义保守写「创房复选规则，完整语义在服务端」，并进待确认清单。
5. 全文写 outPath（templates/ 下）：模板正文原样 + 头部两部分补齐 + 文末「代码锚点索引」「待确认清单」。

## 硬规则

- 证据先行：每条新增/核对的事实必须带代码锚点（文件:行号）；无锚点不写。
- 只读代码：`input-ui/`、`source-code/` 一律不改。
- 正文不动：只动头部两部分（核心需求开篇 + 新增选项小节、名词小节）。
- 禁止猜测：映射不上、语义不明的进待确认清单，不编造定义。
- 编码安全：乱码先归一化再提取。
- 联动语义以实现代码（RuleComp.ts）为准，不以字面猜测。

## 与其他技能的关系

- 产出文档可作为 game-prd-check 的需求文档输入。
- 后续模板正文补齐（开局/行牌等章节）按同模式另行扩展，本技能只管头部。
