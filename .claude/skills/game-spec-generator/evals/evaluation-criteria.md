# 评测标准（evaluation-criteria）

## 加权评分

| 指标 | 权重 | 评法 |
| --- | --- | --- |
| 原始需求覆盖率 | 25% | source-analysis 事实数 vs 原文关键点清单（84 张牌、三种杠、十四种番型、结算公式、全部操作、全部配置项） |
| 规则准确性 | 25% | 抽查 GDD/Contract 中的规则表述与原文逐条比对，错误/改写即扣分 |
| 文档职责分离 | 15% | 玩法规则只在 GDD、产品功能只在 PRD、页面操作只在 Interaction、系统响应只在 Contract；串层即扣分 |
| 交互完整性 | 15% | 每页有主流程+失败/空态；每个主操作有前置条件与反馈 |
| Contract 完整性 | 10% | 14 字段非空率；互斥/超时/失败处理对核心操作全覆盖 |
| 来源追溯率 | 10% | traceability-matrix 中 fully_traced / total_sources |

评分人：人工（产品/策划/程序各至少一人）；AI 只能产出对照材料（覆盖率明细表），不得自评总分。

## 硬性门禁（任一触发即整体不合格，与分数无关）

1. 不允许虚构游戏规则。
2. 不允许把未确认事项标记为已确认（文档 status=approved 或 confirmation_status=confirmed-human 必须由人工标记）。
3. 不允许丢失关键结算公式。
4. 不允许关键规则出现未解释的文档冲突。
5. 不允许 Contract 与 GDD 规则冲突。

## Quality Review 检查清单（第 7 步用）

1. 原始需求覆盖情况（对照基准文件逐项核对）
2. 规则是否丢失
3. 是否产生未经授权的推导（DERIVED 未标注推导依据视同违规）
4. 文档之间是否冲突
5. 交互是否缺少状态和反馈
6. Contract 是否缺少前置条件和异常
7. 是否存在无法追溯的内容（gaps 未登记）
