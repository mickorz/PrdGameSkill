# ui-interaction-prd-extract 产出用作 UI 交互检查规范——可行性分析

- 日期：2026-11-11
- 目标：将 ui-interaction-prd-extract 的逆向产出（客户端代码 + FGUI 交互事实文档）作为**UI 交互检查基准**，检查原始需求文档 `input/【杭州麻将】核心流程杭州麻将好友房AI.md` 中的交互问题。
- 参考：`.opencode-workflows/workflows/game-prd-check.js`（现有 PRD 检查工作流）

## 1. 目标链路

```

```

## 2. 被检查文档画像

`input/【杭州麻将】核心流程杭州麻将好友房AI.md`（578 行，杭州麻将 4 人好友房核心流程）：

- 结构：本期开发范围 / 默认规则 / 功能详情 / 对局流程（桌面布局：对局前、局中信息【方位盘、玩法信息、玩家头像、牌河、手牌】、局内流程【对局开始、定庄、定财神…】、结算流程、辅助功能）
- 交互描述密度高：按钮行为、倒计时配色（03~00 变黄）、断线计时格式（00:00 分秒）、听牌标签优先级（优>大>多>箭头）、理牌动画分步拆解（插入式/平移式）
- **证据大量依赖飞书图片/录屏链接**（feishu.cn internal-api 图片），AI 检查时读不了——这正是逆向产出能补的最大价值：用代码事实替代不可读的截图证据
- 玩法元素：136 张牌、财神（白板财神）、爆头/财飘、庄×1~3（牢数）、东南西北四风位

## 3. 现有 game-prd-check 架构（要复用的东西）

### 3.1 管线八阶段

扫描（input + rules 分组）→ 规则检查（并行 N 组子代理）→ 一致性检查（并行）→ 汇总去重 → 主题归类 → 生成报告 → 报告审核（可自动修正）→ Dashboard

### 3.2 关键机制

- **规则基准目录参数化**：`args.rulesDir` 可指向任意目录——复用管线无需改 workflow，只需准备好规则目录
- 问题五类型：MISSING / CONFLICT / LOGIC / AMBIGUOUS / INCOMPLETE；四级优先级 P0~P3
- 14 字段问题结构（title/location/quote/ruleRef/problem/impact/suggestion/term_explain/required_format/example/acceptance…）
- 12 条硬性要求：证据先行（原文位置+引文）、**以 rules 为准**（需求文档与 rules 冲突时记需求文档的问题）、报前复核、不臆造、不重复等
- 现有规则基准 `references/rules/hzmj_game_flow_handler/`（01-开局~30-重连，30 个主题文件）**本身就是"服务端源码核查"提炼的**——"代码事实作为基准"在本仓库已有先例，逆向产出接入不是新范式，只是新增**客户端 UI 维度**的基准来源

### 3.3 现有基准的覆盖盲区（新基准的切入点）

现有 rules 覆盖服务端游戏流程逻辑（开局/发牌/摸牌/吃碰杠/权限/结算/重连数据），**不含客户端 UI 交互层**：

| 交互维度 | 现有 rules | 逆向产出 |
|---|---|---|
| 按钮组显隐/权限位联动 | 无 | 有（四类限制-前置守卫/互斥） |
| 界面弹层开合时机与层级 | 无 | 有（界面跳转/生命周期） |
| 超时托管默认动作 | 部分（服务端裁决） | 有（客户端表现侧） |
| 断线重连的界面恢复 | 数据侧 | 有（界面侧：askid 恢复、单放牌恢复） |
| 状态机流转 | 无 | 有（表格式状态机） |
| 动效兜底/加载失败恢复 | 无 | 有（超时兜底、包未就绪重挂） |

## 4. 核心问题：基准适用域（必须在检查前裁决）

**逆向代码是卡五星（BoxKaWuXing，3 人、108 张、亮倒/扣牌/漂/马/坎），被检查文档是杭州麻将（4 人、136 张、财神/爆头/财飘）——两个不同玩法。** 不能把卡五星的玩法交互直接当杭麻基准。需要把逆向产出分层：

### L1 引擎级通用交互规范（可跨玩法作为基准）

来源：`base_mahjong/` 公共层 + `common_game/` + 通用弹层模式。典型内容：

- 操作按钮组机制：权限位驱动显隐、多操作并存时"需上报的过"与"本地过"互斥显示、单组合直接执行/多组合展开供选列表
- 交互限制四类模式的通用形态：前置守卫（门闸函数）、互斥（按钮显隐）、超时（托管代打/兜底延迟）、失败恢复（重连按 askid 恢复弹层）
- 结算链模式：结算袋到达 → 等动效播完（带兜底超时）→ 中间页（买马）→ 结算页
- 通用弹层生命周期：showFgui/hideFgui、重连恢复未提交弹层、换房清理残留

### L2 玩法专属交互事实（仅同玩法可比对）

来源：`42324/script/layer|component|protocol`。如亮倒扣牌状态机、选漂/选字、买马页、听口提示（杭麻的听牌标签体系与之不同构）。

**结论**：
- L1 → 可直接作为杭麻文档的 UI 交互检查基准（引擎一致性：xuanwulobby 同仓库同框架，杭麻客户端同样跑在 base_mahjong/common_game 上）
- L2 → 对杭麻检查时**默认不适用**；其真正价值是当被检查对象为**卡五星自己的需求文档**（source-prd/08-UI交互.md）时完全对口
- 检查 prompt 中必须显式声明基准适用域，规则组分组时 L1/L2 分开，L2 组标注"仅适用于同玩法文档检查"

## 5. 接入方案对比

### 方案 A：复用 game-prd-check workflow，传 rulesDir 指向逆向产出目录（推荐起点）

- 做法：`examples/ui-interaction-prd-extract/` 产出直接充当规则目录（每个界面文档 = 一组，界面文档的"状态机/交互限制/测试场景"小节就是可逐条对照的基准条款），调用时 `args.rulesDir='examples/ui-interaction-prd-extract'` + `args.inputFiles=['input/【杭州麻将】...md']`
- 需要的轻量改造：
  1. 逆向文档头部已有文档状态块（status/代码基线），补一行**基准声明**："本文档为客户端代码逆向提取的交互事实基准，作为检查标尺；需求文档与其冲突时记需求文档的问题"
  2. issueRules 补充 UI 交互检查细则（基准适用域声明、L2 组跳过规则、玩法名词映射提示）
- 优点：零管线开发成本；去重/主题归类/报告/审核/Dashboard 全部白得；与现有规则检查可并行跑两轮对比
- 缺点：逆向文档是"实现描述"语态，子代理对照时需要一次"从事实推应有行为"的转换（prompt 一句话可解决）

### 方案 B：转写成规则语态，并入正式规则目录

- 做法：把逆向产出转写为 `references/rules/kwx_ui_interaction/01-主界面交互.md…`（与现有 hzmj_game_flow_handler 同构），之后所有检查自动带上 UI 维度
- 优点：基准语态统一（应有行为），单次检查同时覆盖逻辑+交互
- 缺点：转写有信息损耗风险；卡五星事实"伪装"成杭麻规则有污染基准的风险——除非只转写 L1 部分
- 适合作为方案 A 跑通且 L1 分层验证后的长期形态

### 方案 C：独立 UI 交互专项检查 workflow

- 做法：复制 game-prd-check.js 为 ui-interaction-prd-check.js，规则分组逻辑改为"按界面文档分组"
- 缺点：几乎纯重复（workflow 已完全参数化），违反 YAGNI。**不采纳**

### 推荐路径

1. **第一步**：产出逆向文档（examples/ui-interaction-prd-extract/），L1/L2 分层标注
2. **第二步**：方案 A 跑一轮杭麻文档检查（rulesDir 指向逆向产出 + 基准适用域 prompt），验证报告质量
3. **第三步**：按验证结果决定是否做方案 B 的 L1 转写并入正式规则库

## 6. 交互检查的新增检查点（逆向基准独有的检查能力）

现有规则检查不到、逆向基准才能查的问题类型（对照杭麻文档举例）：

| 检查点 | 基准条款来源 | 杭麻文档上可预期的问题示例 |
|---|---|---|
| 交互限制四类完整性 | 每界面"交互限制"节 | 需求定义了操作但未定义超时/失败行为（如选漂超时默认值，spec-generation 已标 AMB 待确认） |
| 状态机完备性 | 每界面"状态机"节 | 只写了进入态没写退出态；中间态缺失（如弹层打开时收到结算怎么办） |
| 互斥约束 | "互斥"小节 | 两个可同时出现的 UI 状态未定义优先级（断线图标与托管图标并存） |
| 弹层生命周期 | 界面跳转/生命周期表 | 弹层打开时换房/重入的清理行为未定义（代码里 startMatch 统一清残留，需求未必写了） |
| 兜底与降级 | "超时"小节 | 动效异常/资源未就绪的表现未定义（代码有 4s 兜底、重挂机制） |
| 事件时序 | 网络事件关联表 | 需求写了触发但未定义广播到达顺序的界面刷新表现 |

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 基准适用域误用（卡五星事实判杭麻问题） | L1/L2 分组分离 + prompt 显式声明 + L2 组只服务同玩法检查 |
| 代码是"一个版本的现实"，非"需求想要的" | 文档状态块记录代码基线 commit；报告问题类型按现有约定"以 rules 为准"，但 ruleRef 标注"代码逆向基准"，人工复核时可区分 |
| 逆向文档未产出前无法检查 | 本方案前置依赖 examples/ui-interaction-prd-extract/ 正式产出（当前仅有模板与样例） |
| 飞书图片不可读 | 逆向事实恰好补位；报告问题引用 quote 仍以需求文档文本为准 |
| 两轮检查（现有逻辑 + 新交互）结果重复 | workflow 已有去重与同根因标注机制；或分两份报告输出 |

## 8. 落地步骤

1. 产出逆向文档全量（模块/界面分析/流程分析/14 个界面/交互组件），L1/L2 标注
2. 给逆向文档加基准声明头（转写模板一句话）
3. 用方案 A 跑首轮检查：`game-prd-check.js` + `args.rulesDir='examples/ui-interaction-prd-extract'` + `args.inputFiles=['input/【杭州麻将】核心流程杭州麻将好友房AI.md']`
4. 抽查报告中交互类问题的 ruleRef 可溯性（每条应能回到具体界面文档的具体小节）
5. 评估 L1 转写并入正式规则库的收益，决定是否进入方案 B
