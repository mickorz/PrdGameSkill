# ui-interaction-prd-extract 修正报告耗时分析与优化方案

- 分析对象：runId `run-mwee0k70-1`（2026-11-13，消费共享快照 ext-20261112-01）
- 数据来源：`.opencode-workflows/runs/run-mwee0k70-1.json`（32 agent 完整执行记录）、`examples/ui-interaction-prd-extract-workflow/report.md`
- 结论先行：**修正报告阶段合计 3241 秒（约 54 分钟），占整个 run（6098.5 秒）的 53%**；其中 1800 秒是第 1 次尝试超时白烧，且修正闭环对最核心的数据错误（幻觉条款号）零修复。

## 1. 问题现象

```
agent "修正报告" 第 1 次尝试失败，重试: agent "修正报告" 超时 (1800000ms)
```

修正报告 agent 第 1 次尝试撞 30 分钟超时墙全量作废，第 2 次重试约 24 分钟才完成。整个报告审核阶段（审核 288s + 修正 3241s）合计约 59 分钟，超过检查主体阶段。

## 2. 时间线还原（依据 runs 执行记录逐段核对）

## 3. 根因分析

### 根因 1：修正 agent 未指定模型，落到了最慢的默认模型上

工作流脚本中检查、审核 agent 均显式传 `biangfeng-gateway/deepseek-v4.1-flash-official`，唯独修正报告 agent 只传了 `{ agentType: 'general', timeoutMs: 1800000 }`，未传 model，吃到会话默认重型模型。

| agent | 模型 | tokens | 耗时 | 吞吐 |
|---|---|---|---|---|
| 审核报告 | deepseek-flash | 4735 | 288s | 约 16 tok/s |
| 修正报告 attempt 2 | 默认模型 | 3830 | 1441s | 约 2.7 tok/s（含工具往返） |

修正本质是机械的字段改写与核对（读 157KB 报告、对照 72 条 JSON、10 处编辑），不需要重型推理模型。

### 根因 2：超时一刀切 30 分钟 + 失败即全量重启

修正任务的实际负载：整读 157KB 报告（354 行、平均行长 443 字符）、逐条核对 72 条 × 9 字段、10 处精确编辑、编辑后自查。这个负载天然贴近或超过 30 分钟。attempt 1 撞墙后 retry 从零开始，30 分钟工作全部丢弃；attempt 2 用时 1441s，离 30 分钟墙只剩约 6 分钟余量，属于侥幸通过。

### 根因 3：质检问题一半是 workflow 自身规格冲突造出来的

审核报告共发现约 14 条问题，其中 10 条是 MISSING 类问题的「原文」栏格式（应为「需求文档无对应描述」，实际混入了自述说明）。溯源发现这是规格自相矛盾：

- `ISSUES_SCHEMA` 的 quote 字段说明写着「MISSING 类写缺失说明」——检查 agent 照此填自述
- SKILL.md 硬性要求「MISSING 类找不到原文时写明『需求文档无对应描述』」——审核 agent 照此判不合格

下游审核和修正共花了约 59 分钟，其中约 10 条问题完全可以在脚本里一行确定性归一化消除。

### 根因 4：另一半质检问题（幻觉条款号）修正链路根本修不了

检查 agent（flash 模型）编造了规则文件中不存在的条款号：08#36、01#36、07#33、01#42、01#43、02#42、02#43、01#29、06#54（如 01-操作按钮与权限.md 实际条款只有 1~25）。审核 agent 发现了，但修正 prompt 同时硬性要求「不得改动 ID 与基准依据条款号」，修正 agent 只能不修并写长说明。

**已验证最终交付后果：这 9 个幻觉条款号至今仍留在已提交的 report.md 里**（第 53、54、55、56、104 行等位置）。return 值 `reviewOk: true` 具有误导性——修正闭环只修了格式（10 条），对数据错误（条款号）零修复。

### 根因 5：修正发生在乱码检查之后，修正引入的乱码无人复检

工作流的 U+FFFD 乱码检查在分片合并后、审核修正前执行，当时通过。修正 agent 编辑 10 处后自己引入了 2 个 U+FFFD 字符（它声称"修正前已存在"，但引用"原第 996 行"——文件只有 354 行，且合并后的确定性检查是通过的，属于误判自我开脱）。修正之后无任何复检，**乱码已随本次提交进入 report.md**（已验证 FFFD count = 2）。

## 4. 优化方案

### 方案 A：确定性消除（收益最大，治本）

| 编号 | 措施 | 说明 |
|---|---|---|
| A1 | 脚本内确定性归一化 MISSING 的原文栏 | 生成 detailBlocks 前，`type === 'MISSING'` 时 detailField('原文', ...) 固定输出「位置“xxx”。需求文档无对应描述。」，agent 自述移入 problem 字段。10 条质检问题源头消失，零 LLM 成本 |
| A2 | 新增确定性 ruleRef 校验脚本 validate-rulerefs.mjs | 规则条款是 `N.` 有序列表，解析各文件合法条款号集合；生成报告前校验每条 issue 的 ruleRef（NN#M 格式），非法即拦截。参照 merge-parts.mjs 的 commandSuccess 接入方式 |
| A3 | ruleRef 非法时定向重问该组检查 agent | 携带「条款号必须逐字抄自规则文件、报出前先 grep 验证存在」的硬约束重报该组，仍非法则打标记人工处理，不进报告 |
| A4 | 修正后加确定性复检 | FFFD + 统计一致 + ruleRef 再验，放在修正/Dashboard 之前。修正引入的乱码不再漏网 |

预期：修正报告阶段 3241s → 约 0（格式问题 A1 消除、条款号问题 A2/A3 源头拦截后，审核大概率直接通过，修正 agent 不再触发）。

### 方案 B：修好「修」本身的执行参数（治标，立刻可做）

| 编号 | 措施 | 说明 |
|---|---|---|
| B1 | 修正 agent 显式传 analysisModel（flash） | 机械改写不需要重型模型；参照审核 288s，修正预计 5 分钟内 |
| B2 | 修正任务按问题条目分片 | 每条质检问题一个小 agent 只做一个 edit，并行执行；超时损失从 30 分钟全量降到分钟级 |
| B3 | 格式类修正脚本化 | 「重建第 3 节字段行」是纯模板活，可写成 report-fix.mjs 确定性执行，LLM 只兜底非模板问题 |
| B4 | timeoutMs 按实际负载设置（3600000）或省略 | 当前 1800000 与任务负载不匹配，attempt 2 只剩 6 分钟余量 |

### 方案 C：防上游幻觉（可选加固）

- 检查 agent 的 schema/prompt 增加硬约束：「ruleRef 必须逐字抄自规则文件，报出前先验证该条款号存在」
- flash 模型幻觉条款号是本次全部下游浪费（审核发现 → 修正不能修 → 报告残留）的根源，A2 的确定性校验是兜底闸门，两者叠加最稳

### 综合预期

| 项 | 现状 | 优化后 |
|---|---|---|
| 修正报告阶段 | 3241s（占 53%） | 0 ~ 300s |
| 整个 run | ~102 分钟 | ~50 分钟内 |
| 幻觉条款号残留 | 9 个在最终报告 | 0（被 A2 拦截） |
| 乱码残留 | 2 个 U+FFFD 在最终报告 | 0（被 A4 拦截） |

## 5. 遗留问题（本次报告本身的修复项）

1. 已提交的 report.md 残留 9 个幻觉条款号（08#36、01#36、07#33、01#42、01#43、02#42、02#43、01#29、06#54）——正确条款号需回查规则文件与需求原文后人工修正，或按方案 A3 定向重跑对应检查组
2. report.md 末尾残留 2 个 U+FFFD 乱码字符
3. 本次 dashboard 基于含上述缺陷的 report.md 生成，报告修复后需重跑 Dashboard
