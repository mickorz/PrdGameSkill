# PRD Quality Dashboard 设计规范

**文档名称：** dashboard-design.md\
**版本：** v1.0\
**适用项目：** PrdGameSkill / game-prd-check\
**目标：** 将 PRD 检查生成的 report.md 转换为标准化、可复用的 HTML
Dashboard。

------------------------------------------------------------------------

# 1. 项目目标

## 1.1 建设目标

将 game-prd-check Skill 生成的 `report.md` 转换为可视化质量分析
Dashboard。

Dashboard
面向项目负责人、产品经理、策划负责人及开发负责人，帮助他们快速了解：

1.  PRD 整体质量。
2.  问题数量及严重程度。
3.  问题类型与业务模块分布。
4.  当前最值得关注的风险。
5.  检查报告中的具体问题和证据。

## 1.2 产品定位

本项目是 PRD 检查报告的可视化展示层，不负责问题裁决和 PRD 修改。

**本期不包含：**

-   人工裁决操作。
-   问题状态修改。
-   AI 自动修复。
-   PRD 在线编辑。
-   审批工作流。
-   多人协作。

上述能力属于后续独立工作台的范围。

## 1.3 核心设计原则

-   30 秒了解报告整体质量。
-   3 分钟理解主要风险。
-   需要时查看完整问题详情。
-   优先展示结论和风险，而非堆砌数据。
-   保留 report.md 原始信息，不丢失检查证据。

# 2. 页面整体结构

采用单页面纵向 Dashboard。

页面最大宽度：1440px。

页面背景：浅灰色。\
内容区：白色卡片。

页面区块顺序：

  顺序   页面区域       主要内容
  ------ -------------- --------------------------------------
  01     报告头部       项目名称、检查对象、日期、规则基准
  02     质量指标       问题总数、P0、P1、P2/P3
  03     检查结论       整体质量结论、开发阻塞提示
  04     风险分析       开发阻塞、资损风险、重点模块
  05     问题分布       优先级、问题类型、业务模块图表
  06     重点问题       TOP 5 风险问题
  07     完整问题清单   全部问题索引与详情
  08     综合分析       问题集中区域、总体建议、下一阶段建议

所有区域按纵向排列，不使用多 Tab 导航。

# 3. 页面详细设计

## 3.1 报告头部

展示：

-   报告标题：PRD 质量分析报告。
-   项目名称。
-   PRD 文档名称。
-   检查日期。
-   检查规则基准。
-   检查状态。

布局示例：

``` text
PRD 质量分析报告

杭州麻将 · 好友房 AI 核心流程

检查对象：杭州麻将好友房 AI.md
检查日期：2026-11-10
检查基准：游戏流程规范 01~40 + 老 PRD

[存在阻塞问题]
```

头部不放置复杂图表。

## 3.2 核心质量指标

采用四张 KPI 卡片。

  指标            当前报告数据
  ------------- --------------
  问题总数                  45
  P0 严重问题                4
  P1 高优先级               13
  P2/P3                     28

展示规则：

-   数字突出显示。
-   指标名称作为辅助说明。
-   P0 使用红色。
-   P1 使用橙色。
-   P2/P3 使用中性色。
-   卡片支持点击并跳转到问题清单对应筛选结果。

数据必须从 JSON 自动计算。

## 3.3 检查结论

展示报告中的最终判断。

当前报告：

**暂缓进入下一阶段规格生成。**

原因：

1.  AI 专项内容缺失。
2.  超时和断线场景没有兜底。
3.  结算流程不可完整验收。
4.  存在赔付和承包计分风险。

展示形式：

-   结论标签。
-   一段总结文字。
-   关键风险摘要。

不允许 Dashboard 自行推断新的检查结论。

## 3.4 重点风险分析

重点展示两类风险。

### A. 开发阻塞风险

  问题              ID
  ----------------- ---------
  AI 代打机制缺失   PRD-001
  超时没有兜底      PRD-002
  结算流程缺失      PRD-003
  断线重连缺失      PRD-004

展示数量：4 项。

### B. 资损风险

  问题                   ID
  ---------------------- ---------
  三摊摊数口径冲突       PRD-008
  抢杠胡赔付口径冲突     PRD-017
  承包计价与公式不符     PRD-031
  承包与放铳竞合未定义   PRD-032

展示数量：4 项。

每项风险需要展示：

-   风险名称。
-   问题 ID。
-   优先级。
-   风险说明。
-   点击后定位到问题详情。

注意：风险分类可以交叉，同一问题可以同时属于优先级分类、问题类型分类和风险专题。不同分类不得相加计算总问题数。

## 3.5 问题分布分析

本区域使用三个图表。

### 图表 A：优先级分布

类型：横向进度条。

  优先级     数量     占比
  -------- ------ --------
  P0            4    8.89%
  P1           13   28.89%
  P2           20   44.44%
  P3            8   17.78%

要求：

-   显示数量。
-   显示占比。
-   颜色与全站优先级保持一致。
-   点击优先级过滤问题列表。

### 图表 B：问题类型分布

类型：环形图。

  类型           数量
  ------------ ------
  需求缺失          18
  内容冲突          8
  逻辑错误             4
  定义歧义         6
  描述不完整        9

类型中文说明：

  类型         中文
  ------------ ------------
  需求缺失      需求缺失
  内容冲突     内容冲突
  逻辑错误        逻辑错误
  定义歧义    定义歧义
  描述不完整   描述不完整

要求：

-   展示数量。
-   展示占比。
-   Hover 显示类型说明。
-   点击类型过滤问题列表。

### 图表 C：重点业务模块分布

类型：横向柱状图。

  模块           问题数量
  ------------ ----------
  行牌与操作           12
  结算链路             11
  对局框架              9

注意：

这三个模块是报告总结中列出的重点问题集合，不是完整互斥分类。不能将它们作为全部
45 条问题的完整分布。

后续标准化时，可以增加完整的模块分类字段。

要求：

-   按问题数量降序排列。
-   显示模块名称及数量。
-   点击模块筛选问题。
-   允许未来增加其他模块。

## 3.6 重点问题 TOP 5

采用紧凑型问题卡片或表格。

  ID        问题                          优先级
  --------- ----------------------------- --------
  PRD-001   AI 代打机制全文缺失           P0
  PRD-002   无托管且无超时兜底            P0
  PRD-003   结算流程关键步骤整体缺失      P0
  PRD-004   断线重连恢复流程整体缺失      P0
  PRD-017   抢杠胡赔付与老 PRD 基准冲突   P1

TOP 5 的排序依据：

1.  开发阻塞。
2.  资损风险。
3.  优先级。
4.  报告中的影响程度。

这是重点展示集合，不改变原始问题优先级。

## 3.7 完整问题清单

展示 report.md 中全部问题。

默认展示字段：

  字段       说明
  ---------- ---------------
  ID         PRD-001
  问题标题   问题名称
  优先级     P0/P1/P2/P3
  类型       需求缺失 等
  原文位置   对应 PRD 章节

支持：

-   按优先级筛选。
-   按问题类型筛选。
-   按业务模块筛选（有完整模块数据时）。
-   按关键词搜索。
-   按 ID 搜索。
-   按优先级排序。
-   恢复全部问题视图。

默认排序：P0 → P1 → P2 → P3，同级按 ID 升序。

### 问题详情抽屉

点击问题行，在右侧展开详情。

详情内容：

1.  问题 ID、标题、优先级、类型。
2.  原文引用。
3.  问题分析。
4.  影响说明。
5.  修改建议。
6.  原始处理状态。

原始处理状态只读展示。

不提供采纳、修改、否决、挂起等按钮。

抽屉要求：

-   支持关闭。
-   支持上一条/下一条问题。
-   不改变当前筛选条件。
-   手机端转换为全屏详情面板。

## 3.8 综合分析与结论

展示 report.md 的总体建议。

包含：

-   问题最多的模块。
-   可能影响开发的问题。
-   是否建议进入下一阶段。
-   后续优先处理建议。

必须保留报告原有结论，不允许自动生成与原报告相矛盾的判断。

# 4. 交互设计规范

本项目以浏览和分析为主。

  交互             行为
  ---------------- ---------------------------
  点击 KPI         跳转问题列表并应用筛选
  点击优先级图表   按优先级筛选
  点击问题类型     按问题类型筛选
  点击模块柱状图   按模块筛选
  点击重点问题     展开对应详情
  点击问题列表行   展开右侧抽屉
  点击清除筛选     恢复完整问题列表
  点击返回顶部     回到页面顶部
  点击导出         进入浏览器打印 / PDF 流程

筛选状态统一管理，避免图表和列表各自维护不同的筛选条件。

不实现裁决和修改操作。

# 5. 视觉设计规范

## 5.1 设计风格

现代简洁企业级 SaaS 风格，参考 Linear、Stripe Dashboard、GitHub Insights
的简洁信息组织方式，不直接复制其页面。

## 5.2 色彩

  用途       色值
  ---------- ---------
  页面背景   #F6F8FB
  卡片背景   #FFFFFF
  主色       #3478DB
  P0         #DC5148
  P1         #E8A044
  P2         #4389D5
  P3         #94A3B8
  正文       #253247
  辅助文字   #8491A3
  边框       #E7ECF2

## 5.3 布局

-   页面最大宽度：1440px。
-   页面居中。
-   卡片圆角：10～12px。
-   卡片间距：16～24px。
-   页面采用舒适型信息密度。
-   图表不使用大面积渐变。
-   不使用过多彩色徽章。
-   使用统一图标体系。

## 5.4 响应式

桌面端： - 1440px：充分利用双列布局。 - 1024px：部分双列区域调整为单列。

平板端： - KPI 卡片两列。 - 图表两列或单列。

手机端： - 所有内容单列。 - 图表自适应。 - 问题表格转为问题卡片。 -
详情抽屉转为全屏页面。

# 6. 技术架构与数据规范

## 6.1 数据处理流程

``` text
report.md
    |
    v
Report Parser
    |
    v
report.json
    |
    v
Data Validator
    |
    v
Dashboard Renderer
    |
    v
index.html
```

原则：

-   Markdown 是原始报告来源。
-   JSON 是 Dashboard 的标准数据输入。
-   HTML 不直接解析 Markdown。
-   页面不写死具体项目名称和统计数据。
-   不允许统计数据与问题明细脱节。

## 6.2 建议目录

``` text
game-prd-check/
├── scripts/
│   └── build-dashboard.py
├── dashboard/
│   ├── index.html
│   ├── assets/
│   │   ├── css/
│   │   │   └── dashboard.css
│   │   ├── js/
│   │   │   ├── app.js
│   │   │   ├── charts.js
│   │   │   ├── filters.js
│   │   │   └── issue-detail.js
│   │   └── icons/
│   └── schema/
│       └── report.schema.json
└── output/
    ├── report.md
    ├── report.json
    └── dashboard/
        └── index.html
```

具体目录可根据 Skill 当前结构调整，不强制迁移现有目录。

## 6.3 report.json 数据模型

``` json
{
  "schema_version": 1,
  "report": {
    "title": "PRD 质量分析报告",
    "project_name": "杭州麻将",
    "document_name": "好友房 AI 核心流程",
    "inspection_date": "2026-11-10",
    "source_file": "report.md",
    "rule_baselines": [],
    "overall_conclusion": {
      "status": "BLOCKED",
      "summary": "暂缓进入下一阶段规格生成",
      "reasons": []
    }
  },
  "statistics": {
    "total": 45,
    "priority": {
      "P0": 4,
      "P1": 13,
      "P2": 20,
      "P3": 8
    },
    "types": {
      "需求缺失": 18,
      "内容冲突": 8,
      "逻辑错误": 4,
      "定义歧义": 6,
      "描述不完整": 9
    }
  },
  "risk_groups": [],
  "modules": [],
  "featured_issues": [],
  "issues": [
    {
      "id": "PRD-001",
      "title": "AI 代打机制全文缺失",
      "priority": "P0",
      "type": "需求缺失",
      "module": [],
      "source_location": "全文",
      "original_text": "...",
      "problem": "...",
      "impact": "...",
      "suggestion": "...",
      "status": "待确认"
    }
  ],
  "overall_recommendations": []
}
```

数据约束：

-   issues 是完整问题数据的唯一来源。
-   statistics 默认由 issues 计算。
-   modules 允许一个问题关联多个模块。
-   risk_groups 允许多个风险集合交叉引用同一问题。
-   featured_issues 通过 ID 引用 issues，不复制问题正文。
-   原始文本和建议不得丢失。
-   不存在的字段使用空值或空数组，不得编造。

## 6.4 数据校验

生成 Dashboard 前必须检查：

1.  问题 ID 唯一。
2.  问题总数与明细数量一致。
3.  P0～P3 统计总和与问题总数一致。
4.  五种问题类型统计总和与问题总数一致。
5.  风险集合引用的问题 ID 均存在。
6.  TOP 5 引用的问题 ID 均存在。
7.  原文、问题、影响、建议等字段正确保留。
8.  不支持的字段不得被静默丢弃。

统计不一致时应报告错误，不应继续生成一份看似正常的 Dashboard。

# 7. 导出与展示

V1 支持：

-   浏览器直接打开 HTML。
-   本地静态访问。
-   浏览器打印。
-   打印为 PDF。

打印模式要求：

-   隐藏搜索和筛选控件。
-   展开重点问题内容。
-   避免卡片和表格跨页截断。
-   保留图表和颜色。
-   显示报告元信息。

Dashboard 必须支持离线使用，不依赖运行时 API。

如果图表库使用外部 CDN，应提供本地依赖方案，保证离线打开仍可用。

# 8. Skill 集成要求

本 Dashboard 是 game-prd-check Skill 的标准化输出能力。

执行流程：

``` text
用户提交 PRD
    |
    v
game-prd-check Skill
    |
    v
生成 report.md
    |
    v
Dashboard Parser
    |
    v
生成 report.json
    |
    v
Schema Validation
    |
    v
生成 Dashboard HTML
    |
    v
输出报告路径
```

Skill 的最终交付物：

``` text
output/
├── report.md
├── report.json
└── dashboard/
    └── index.html
```

用户只需要打开 index.html，即可查看可视化报告。

不同项目、不同游戏、不同 PRD 检查报告均使用同一套 Dashboard 模板。

# 9. 验收标准

## Gate A：数据解析

-   [ ] 正确解析 report.md。
-   [ ] 45 条问题全部进入 JSON。
-   [ ] 统计数据与原报告一致。
-   [ ] 五种问题类型正确。
-   [ ] P0～P3 优先级正确。
-   [ ] 原文、问题、影响、建议完整保留。
-   [ ] 风险集合正确引用问题 ID。

## Gate B：Dashboard 展示

-   [ ] 八个页面区域完整展示。
-   [ ] KPI 数量正确。
-   [ ] 三类图表正确。
-   [ ] 风险摘要正确。
-   [ ] TOP 5 正确。
-   [ ] 全部问题能够查看。
-   [ ] 详情抽屉正确展示。
-   [ ] 搜索和筛选正常。
-   [ ] 点击图表可以联动问题清单。

## Gate C：通用化

-   [ ] 不依赖杭州麻将的固定数据。
-   [ ] 支持不同项目名称。
-   [ ] 支持不同数量的问题。
-   [ ] 支持未来增加问题类型。
-   [ ] 支持未来增加业务模块。
-   [ ] 更换 report.json 即可生成新的报告。
-   [ ] 无外部 API 依赖。
-   [ ] HTML 离线可打开。
-   [ ] 打印与 PDF 输出正常。

## Gate D：视觉与体验

-   [ ] 现代简洁浅色风格。
-   [ ] 信息密度舒适。
-   [ ] 桌面端显示正常。
-   [ ] 手机端显示正常。
-   [ ] 图表与正文视觉统一。
-   [ ] 长文本不溢出。
-   [ ] 详情抽屉不遮挡主要内容。
-   [ ] 打印页面布局正常。

# 10. V1 开发优先级

  阶段   工作内容                              优先级
  ------ ------------------------------------- --------
  T1     report.md → report.json 解析与校验    P0
  T2     Dashboard 页面骨架、KPI、风险、图表   P0
  T3     问题列表、搜索筛选、详情抽屉          P1
  T4     打印、PDF、响应式、通用化验收         P1

**V1 核心 DoD：**

给定任意符合约定结构的 PRD 检查
report.md，能够自动生成数据正确、视觉统一、可离线打开的 Dashboard HTML。

不允许为了完成页面而丢失原始检查信息，也不允许在 Dashboard
层擅自改变报告的检查结论。

# 11. 后续扩展（不属于 V1）

未来可以考虑：

-   多份 PRD 报告横向比较。
-   同一 PRD 多次检查的质量变化。
-   问题类型趋势。
-   模块风险变化。
-   问题裁决工作台。
-   AI 自动生成修改建议。
-   修改前后质量对比。
-   PRD 质量评分。

这些能力不应影响 V1 的交付。

**最终产品定位：Dashboard 是 PRD
检查报告的标准可视化呈现层，不是问题处理工作台。**
