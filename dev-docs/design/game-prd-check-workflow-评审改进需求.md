## 〇、目标演进（v2 的定位）

| | 现状（问题发现型） | 目标（全量覆盖审计型） |
|---|---|---|
| 输出 | 只输出发现的问题（缺失/冲突/不完整） | 列出所有应检查的需求点 × Rule 对应关系 × 检查结果；**完全正确的需求点也保留在报告中** |

## 一、核心设计：双向追踪矩阵（RTM）

### 1.1 双向追踪（最重要的设计决定）

| 方向 | 做什么 | 发现什么 |
|---|---|---|
| Rule → PRD | 从规则出发，检查所有要求是否有对应需求描述 | 遗漏、覆盖缺口 |
| PRD → Rule | 从原始需求出发，为每个需求点找检查依据 | 无依据、额外需求 |

**关键判定纪律**：
- Rule 无对应 PRD ≠ 一定是需求缺失（先判断 Rule 是否属本次检查范围、是否强制）
- PRD 无对应 Rule ≠ 一定是错误（可能是合理新需求，标"**无规则对应，待确认**"，不直接定问题）
- 支持多对多映射：一条 Rule 对多条需求、多条 Rule 对一条需求（ruleRefs 必须是数组）

### 1.2 数据结构（稳定 ID，不随运行重新编号）

**requirements-matrix.json**（机器可读唯一事实源）：

```json
{
  "requirementId": "REQ-001",
  "title": "开局发牌",
  "source": { "file": "input/game.md", "section": "2.1", "fromLine": 20, "toLine": 35 },
  "ruleRefs": [
    {
      "ruleId": "RULE-001",
      "file": "references/rules/发牌规则.md",
      "section": "3.1",
      "relationship": "direct",
      "status": "pass",
      "evidence": "对应原文及判断依据"
    }
  ],
  "overallStatus": "pass",
  "issueIds": []
}
```

**rule-catalog.json**（规则反向目录，独立保存，不可省略）：

完全遗漏的需求在 PRD 中根本不存在，无法从 PRD 提取——必须从规则目录**反向生成**预期需求点，再与原始需求匹配。rule-catalog 记录所有 Rule 的原子检查点、来源位置、检查范围、重要性。

**映射状态枚举**：`pass / incomplete（不完整）/ conflict（冲突）/ missing（缺失）/ unverified（未验证）/ na（不适用）/ pending-confirm（无规则对应，待确认）`

**问题实体规范化**：同一问题即使影响多个需求或规则，也只建一个规范化问题实体，通过 ID 关联（对应 v1-T2 的 rawIssues/canonicalIssues/duplicateLinks 分层）。

### 1.3 AI 与脚本的分工（v1-T4 升级为核心原则）

AI 只生成结构化检查数据（矩阵条目、判断依据），**Markdown/Dashboard/JSON 全部由确定性脚本生成**。需求点达到几百上千条时，输出不会因模型响应长度限制截断。

## 二、阶段调整（保留并行架构）

| 阶段 | 现有功能 | 调整后 |
|---|---|---|
| 1. 扫描 | 扫描 PRD 和 Rule 文件 | 保留 |
| 2. 需求提取 | 无 | **新增**：提取全部 PRD 需求点 + Rule 原子检查点（产出 requirements.json 草稿与 rule-catalog.json） |
| 3. 规则检查 | 只输出发现的问题 | 输出**每条规则检查点的覆盖记录 + 发现的问题** |
| 4. 一致性检查 | 发现内部冲突 | 保留，关联需求 ID |
| 5. 汇总去重 | 合并问题 | 合并问题 + **完整追踪矩阵组装** |
| 6. 主题归类 | 按问题归类 | 保留 |
| 7. 报告生成 | 问题报告 | **全量矩阵 + 问题报告**（确定性脚本生成） |
| 8. 报告审核 | 检查格式 | 增加**需求覆盖、规则覆盖、映射完整性**验证 |
| 9. Dashboard | 问题统计 | 增加**全量需求追踪页面**（交互筛选后置到第二阶段） |

## 三、报告结构（report.md 调整）

1. 检查概览：需求总数、规则总数、已检查数量、通过数量、存在问题数量、未验证数量
2. **全量需求追踪矩阵**：逐条列出所有需求及关联 Rule（新增）
3. **Rule 覆盖矩阵**：逐条列出所有适用规则及对应 PRD（新增）
4. 问题清单：保留现有 P0~P3
5. 重点问题详情：保留
6. 检查结论：是否存在规则未覆盖、检查失败或待确认项

Dashboard 矩阵页支持点击需求点查看原文、Rule 原文、判断依据及关联问题（筛选：全部/通过/不完整/冲突/缺失/未验证——第二阶段）。

## 四、验收硬条件（7 条）

1. 每个被识别出的 PRD 原子需求点必须出现在矩阵中，不能只展示存在问题的需求
2. 每个适用的 Rule 原子检查点必须有覆盖记录；没有对应 PRD 的也必须列出
3. 每条需求与 Rule 的关联必须能追溯到源文件、章节或行号
4. 每条映射必须有明确状态（通过/不完整/冲突/缺失/未验证/不适用/待确认）
5. 任何检查组失败，对应需求点**不得默认标通过**（对接 v1-T1 的 coverageStatus：partial 时矩阵状态只能标 unverified）
6. 问题实体规范化：一问题一实体，ID 关联，不重复计数
7. report.md、Dashboard、JSON 三者统计一致

## 六、关键注意（实施时防坑）

1. **不要用 AI 手写整份全量报告**——矩阵上百条时必截断；AI 产结构化数据，脚本产报告
2. **Rule→PRD 缺口不可武断定缺失**——先过"检查范围/强制性"过滤，未确认的标 pending-confirm
3. **规则原子检查点粒度**——rule-catalog 拆到"单条可判定"粒度（如 UI 基准的 `01#3`），避免"一个文件一条"导致覆盖记录失真
4. **稳定 ID 的持久化**——REQ-xxx/RULE-xxx 需跨运行稳定（按源文件+行号/锚点哈希生成），否则矩阵无法对比两次检查
5. **与 ui-interaction-prd-extract 同步**——同源结构，RTM 落地后需同步（其基准已有 01#N 条款号体系，rule-catalog 可直接复用）
6. **与 rule-checklist 汇报需求的联动**——RTM 的矩阵统计就是《需要记录检查过的rule-checklist》要的"总检查项/通过数/通过率"，落地后合并展示
