> **v3 补充 4 项关键设计细则、4 个待确认项定案、第一阶段三步实施顺序（2026-11-12）**
> 评审对象：[.opencode-workflows/workflows/game-prd-check.js](../../.opencode-workflows/workflows/game-prd-check.js)
> 状态：需求定稿，可交开发 Agent 实施；v1 P0/P1 论断已对照源码核实属实

## 〇、目标定位

把 workflow 从"问题发现型"升级为"需求全量覆盖审计型"（RTM）：

| | 现状 | 目标 |
|---|---|---|
| 输出 | 只输出发现的问题 | 所有需求点 × Rule 对应关系 × 检查结果；完全正确的需求点也保留 |
| 回答 | "PRD 有哪些问题" | "PRD 有哪些需求、每个需求受哪些 Rule 约束、每条 Rule 是否被覆盖、哪些需要修改" |
| 汇报 | 问题清单 | 工作量与覆盖面可量化（区分检查完成率与通过率） |

**总原则（v3 定案）**：规则覆盖完整 ≠ 需求正确；需求有对应 Rule ≠ 检查通过。
追踪关系（映射）、检查执行状态（完成/失败/跳过）、规则符合性判断（pass/conflict/...）**三者分开记录**，不可混用。

实施约束：保留现有并行检查架构，不整体重写。

## 一、双向追踪矩阵（RTM）核心设计

### 1.1 双向追踪

| 方向 | 做什么 | 发现什么 |
|---|---|---|
| Rule → PRD | 从规则出发，检查所有要求是否有对应需求描述 | 遗漏、覆盖缺口 |
| PRD → Rule | 从原始需求出发，为每个需求点找检查依据 | 无依据、额外需求 |

判定纪律：Rule 无对应 PRD ≠ 一定缺失（先判范围/强制性）；PRD 无对应 Rule ≠ 一定错误（可能合理新需求，标"无规则对应，待确认"）。映射支持多对多（ruleRefs 数组）。

### 1.2 数据结构与落盘布局

**output/ 目录（结构化数据先于报告落盘，每个检查 Agent 独立 JSON）**：

```text
output/
  rule-catalog.json          # 规则原子检查点目录（反向生成，独立保存）
  requirements.json          # PRD 需求点清单
  identity-map.json          # 需求点持久化 ID 映射表（跨运行复用）
  checks/
    group-001.json           # 每个规则组的覆盖记录 + 问题（独立分片）
    group-002.json
    ...
  requirements-matrix.json   # 组装后的追踪矩阵（唯一事实源）
  issues.json                # 规范化问题实体
  report.md                  # 确定性脚本生成
```

分片落盘的收益：某组失败可定位失败范围；重跑时复用已完成且仍有效的分片，不必所有 Agent 重跑。

**矩阵条目结构**：

```json
{
  "requirementId": "REQ-001",
  "title": "开局发牌",
  "source": { "file": "input/game.md", "section": "2.1", "fromLine": 20, "toLine": 35 },
  "ruleRefs": [
    {
      "ruleId": "RULE-001",
      "file": "references/rules/发牌规则.md",
      "section": "3.1",
      "relationship": "direct",
      "status": "pass",
      "evidence": "对应原文及判断依据"
    }
  ],
  "overallStatus": "pass",
  "issueIds": []
}
```

### 1.3 AI 与脚本分工

AI 只生成结构化检查数据；Markdown/Dashboard/JSON 统计由确定性脚本生成。需求点到几百上千条时不因模型响应长度截断。

## 二、关键设计细则（v3 新增，开发前必须遵守）

### 2.1 需求点拆分标准（P0）

**标准：一个原子需求点 = 能独立判断是否满足某项预期行为或验收条件。**

示例——原文"玩家可以碰牌，碰牌后需要广播给其他玩家，并更新自己的手牌"拆为：

- REQ-001：玩家满足条件时可以碰牌
- REQ-002：碰牌成功后向其他玩家广播
- REQ-003：碰牌成功后更新玩家手牌

边界：不要机械逐句切分，避免大量无业务价值的碎片。

**分工定案**：AI 按独立可验证行为提取；**脚本负责结构和完整性校验**（防漏、防碎片化超限）。

### 2.2 稳定 ID 策略（P0）

**禁止直接用行号/哈希生成 ID**——PRD 插入一段文字，后续行号全部漂移，导致大批需求 ID 变化、矩阵无法跨运行对比。

采用持久化 ID 映射表：

```text
requirements.json -> identity-map.json -> 下一轮检查复用已有 ID
```

- 新需求点通过"来源锚点 + 规范化文本 + 历史匹配"识别是否为已有需求
- 匹配不确定时**标记待确认，禁止自动合并**为同一需求

### 2.3 指标定义：完成率与通过率必须分开（P0）

覆盖率必须有明确分母，示例口径：

```text
规则原子检查点总数   300
本次适用规则点       260   （适用性未确认的不得剔除出分母）
成功完成检查         240
未完成检查            20
已通过检查           210
```

两个指标严格区分：

```text
检查完成率 = 已完成检查的适用规则点数 / 全部适用规则点数
规则通过率 = 已通过的适用规则点数 / 已完成检查的适用规则点数
```

**禁止把完成率当通过率**——否则未检查部分被掩盖。

### 2.4 检查组失败的处理（承 v1-T1）

任何检查组失败：对应需求点/规则点状态只能标 `unverified`，**不得默认通过**；报告与 Dashboard 显式展示完成率与失败组清单。

## 三、阶段调整（保留并行架构）

| 阶段 | 现有功能 | 调整后 |
|---|---|---|
| 1. 扫描 | 扫描 PRD 和 Rule 文件 | 保留 |
| 2. 需求提取 | 无 | **新增**：提取全部 PRD 需求点 + Rule 原子检查点 |
| 3. 规则检查 | 只输出问题 | 输出每条规则检查点的**覆盖记录 + 问题**（独立分片 JSON） |
| 4. 一致性检查 | 发现内部冲突 | 保留，关联需求 ID |
| 5. 汇总去重 | 合并问题 | 合并问题 + **矩阵组装**（确定性） |
| 6. 主题归类 | 按问题归类 | 保留 |
| 7. 报告生成 | 问题报告 | **全量矩阵 + 问题报告**（确定性脚本） |
| 8. 报告审核 | 检查格式 | 增加**需求覆盖、规则覆盖、映射完整性**校验 |
| 9. Dashboard | 问题统计 | 全量需求追踪页（交互筛选后置第二阶段） |

## 四、报告结构

1. 检查概览：需求总数、规则检查点总数、适用数、已完成数、通过数、有问题数、未验证数（完成率与通过率分列）
2. 全量需求追踪矩阵（新增）
3. Rule 覆盖矩阵（新增）
4. 问题清单（保留 P0~P3）
5. 重点问题详情（保留）
6. 检查结论：规则未覆盖、检查失败、待确认项

## 五、验收硬条件

1. 每个被识别的 PRD 原子需求点必须出现在矩阵中（不只展示有问题的）
2. 每个适用 Rule 原子检查点必须有覆盖记录；无对应 PRD 的也必须列出
3. 每条需求-Rule 关联可追溯到源文件、章节或行号
4. 每条映射有明确状态（pass/incomplete/conflict/missing/unverified/na/pending-confirm）
5. 检查组失败 → 对应项标 unverified，不得默认通过
6. 问题实体规范化：一问题一实体，ID 关联，不重复计数
7. report.md、Dashboard、JSON 三者统计一致
8. **完成率与通过率分列展示，不得混用**（v3 新增）

## 六、待确认问题 → 已定案（v3）

| 待确认项 | 定案 |
|---|---|
| 需求提取粒度 | AI 按独立可验证行为提取（2.1 标准），脚本负责结构和完整性校验 |
| Rule 来源 | **先从现有 rules 目录生成 rule-catalog，不要求立即重写 41 个规则文件** |
| Agent 并发规模 | 保留 16 并发上限；**分片任务数量不必限制为 16 或 24**（分片是数据组织单位，不是并发单位） |
| 未验证项容忍度 | 允许生成部分结果但必须显式标记；**完整审计的验收要求所有适用规则完成检查** |

## 七、实施路线

| 阶段 | 内容 | 验收物 |
|---|---|---|
| **T1 全量需求与 Rule 原子化** | 提取 requirements.json + rule-catalog.json；校验原始文件全覆盖（PRD 章节、规则条款不漏） | 两份 JSON + 覆盖校验结果 |

| 第二阶段 | Dashboard 全量需求追踪页（交互筛选、问题跳转、审批联动） | 复用 merge-prd-dashboard 的 Tab 思路扩展 |

## 八、关键注意（实施防坑）

1. 不要用 AI 手写整份全量报告——矩阵上百条必截断；AI 产数据、脚本产报告
2. Rule→PRD 缺口不可武断定缺失——先过范围/强制性过滤，未确认标 pending-confirm
3. 规则原子检查点拆到"单条可判定"粒度（如 UI 基准 `01#3`），避免"一文件一条"失真
4. 与 ui-interaction-prd-extract 同步——其基准已有 `01#N` 条款号体系，rule-catalog 可直接复用
5. 与 rule-checklist 汇报需求联动——RTM 矩阵统计就是《需要记录检查过的rule-checklist-分析方案.md》要的"总检查项/通过数/通过率"，落地后合并展示（注意用 2.3 的双指标口径）
