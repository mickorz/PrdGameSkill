## 背景

核心目标：快速从原始 PRD 中找出真正影响开发的问题，生成可交给策划处理的报告。
评审认可架构（扫描分组 → 并行规则检查 → 一致性检查 → 汇总去重 → 报告 → Dashboard）值得保留，
问题集中在**结果可信度**与**执行效率**两类。

## 改造路线（评审建议优先级，按目标"尽快获得可信报告"排序）

| 阶段 | 内容 | 优先级 | 要点 |
|---|---|---|---|
| T1 | 检查覆盖率与失败组标记 | 优先 | return/报告/Dashboard 增加 `coverageStatus`（complete/partial/failed）、`failedGroups`、`coverageRate`；partial 时 Dashboard 顶部明示"检查不完整"，问题总数不得当作完整结论 |
| T2 | 统一去重与统计口径 | 优先 | 数据分三层：`rawIssues`（原始发现）/ `canonicalIssues`（去重后）/ `duplicateLinks`（同根因引用）；统计一律以 canonicalIssues 为准；两条去重路径行为对齐（重复项保留 + 标注，不静默删除） |
| T3 | 引文与规则引用验证 | 优先 | 新增确定性验证阶段：quote 与需求原文逐字核对、ruleRef 条款存在性校验、location 定位核对；语义判断（缺失是否成立、引用是否支持结论）再交 AI 复核 |
| T4 | JS 确定性生成 Markdown/JSON | 第二批 | 已有结构化 ISSUES_SCHEMA，表格/统计/清单由 JS 直接拼装，Agent 只产出推理与解释性内容；写盘从"Agent 写文件"改为"JS 写文件" |
| T5 | 文档索引减少重复读取 | 第二批 | 预处理建共享章节索引（章节 ID/来源/行号/关键词），规则组按相关性分发材料；跨章节引用按需补读；**注意**：缺失类判定不能只凭语义检索片段，每个规则点要有明确检查范围与覆盖证据，不确定标"待复核"，防误报 |
| T6 | 增量审核与结果缓存 | 后续 | 未变化的规则组/章节跳过重查 |

## 三个目标指标（改造验收口径）

1. **检查覆盖率**：应检查的规则是否全部完成检查（T1 落地后可量化）
2. **问题可信度**：每条问题有可追溯、可复核的证据（T3 落地后可量化）
3. **有效问题数**：去重后需要策划确认/修改的真实数量（T2 落地后口径唯一）

三个指标可靠后再做 Token/缓存/耗时优化（T4~T6），收益才有意义。
