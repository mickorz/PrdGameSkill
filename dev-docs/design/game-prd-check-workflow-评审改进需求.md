## 〇、目标定位

把 workflow 从"问题发现型"升级为"需求全量覆盖审计型"（RTM）：

| | 现状 | 目标 |
|---|---|---|
| 输出 | 只输出发现的问题 | 所有需求点 × Rule 对应关系 × 检查结果；完全正确的需求点也保留 |
| 回答 | "PRD 有哪些问题" | "PRD 有哪些需求、每个需求受哪些 Rule 约束、每条 Rule 是否被覆盖、哪些需要修改" |
| 汇报 | 问题清单 | 工作量与覆盖面可量化（区分检查完成率与通过率） |

**总原则**：规则覆盖完整 ≠ 需求正确；需求有对应 Rule ≠ 检查通过。
追踪关系（映射）、检查执行状态（完成/失败/跳过）、规则符合性判断（pass/conflict/...）**三者分开记录**。

实施约束：保留现有并行检查架构，不整体重写。

**第一阶段最重要的验收不是生成多少条问题，而是**：所有识别出的需求点都在清单里、所有适用 Rule 都有检查记录、每条检查结果都有可验证依据。做到这一步，game-prd-check 才从一次性的 PRD 问题检查工具，升级为可反复执行、可追溯的游戏需求质量审计系统。

## 一、双向追踪矩阵（RTM）核心设计

### 1.1 双向追踪

| 方向 | 做什么 | 发现什么 |
|---|---|---|
| Rule → PRD | 从规则出发，检查所有要求是否有对应需求描述 | 遗漏、覆盖缺口 |
| PRD → Rule | 从原始需求出发，为每个需求点找检查依据 | 无依据、额外需求 |

判定纪律：Rule 无对应 PRD ≠ 一定缺失（先判范围/强制性）；PRD 无对应 Rule ≠ 一定错误（可能合理新需求，标"无规则对应，待确认"）。映射支持多对多（ruleRefs 数组）。

### 1.2 数据结构与落盘布局（v4 改为运行快照制）

```text
output/
  identity-map.json              # 需求点持久化 ID 映射表（跨运行共享，唯一不按运行隔离）
  runs/
    run-20261112-001/            # 每次运行独立快照，不覆盖历史
      manifest.json              # 运行清单（时间、输入指纹、配置、统计摘要）
      rule-catalog.json
      requirements.json
      checks/
        group-001.json           # 每个规则组独立分片
        ...
      requirements-matrix.json   # 组装后的追踪矩阵（唯一事实源）
      issues.json                # 规范化问题实体
      report.md                  # 确定性脚本生成
```

快照制收益（跨运行对比）：
- 本次新增了哪些需求、哪些原有需求被删除或修改
- 哪些问题已解决、哪些是新出现
- 历史审计可追溯，策划改完需求后重跑不会覆盖上次结论

### 1.3 AI 与脚本分工

AI 只生成结构化检查数据；Markdown/Dashboard/JSON 统计由确定性脚本生成。需求点到几百上千条时不因模型响应长度截断。

### 1.4 证据校验规则（v4 新增，P0，必须可执行）

每条矩阵记录（含 ruleRefs 与 issueIds）落地前过以下确定性校验：

| # | 校验项 | 不合格处理 |
|---|---|---|
| 1 | `source.file` 文件存在 | 该记录标 `unverified` |
| 2 | `fromLine/toLine` 有效（正序、在文件行数内） | 同上 |
| 3 | 引用文本与源文件对应行范围一致 | 同上 |
| 4 | `ruleId` 存在于 rule-catalog.json | 该 ruleRef 标 `unverified` |
| 5 | issueIds 关联的 requirementId 存在于矩阵 | 关联剔除并记警告 |
| 6 | 检查组失败（manifest 记录） | 对应项只能标 `unverified` |

**边界声明**：脚本只能验证**引用的真实性**与**关联完整性**，不能验证 AI 语义判断是否正确（如"缺失是否成立""引用是否支持结论"）——语义复核仍由 AI 复核/报告质检承担，两层不可互相替代。

### 1.5 分片恢复契约（v4 新增，P1，本阶段只做数据契约）

每个分片 JSON 头部必须记录：

```json
{
  "groupId": "group-001",
  "status": "completed",
  "inputFingerprint": "sha256...",
  "ruleFingerprint": "sha256...",
  "checkVersion": "v1",
  "resultPath": "checks/group-001.json"
}
```

复用条件：`inputFingerprint`（PRD 输入指纹）、`ruleFingerprint`（规则指纹）、`checkVersion`（检查逻辑版本）**三者全部匹配**才允许复用；任一变化即过期，需重跑该组。
（防止 PRD 已修改却复用昨日结论产生过期结果。真正的增量缓存优化仍按计划放后续，本阶段只固化契约字段。）

### 1.6 AI 与脚本分工

AI 只生成结构化检查数据；Markdown/Dashboard/JSON 统计由确定性脚本生成。需求点到几百上千条时不因模型响应长度截断。

## 二、关键设计细则（v3 定案，保持有效）

### 2.1 需求点拆分标准（P0）

**标准：一个原子需求点 = 能独立判断是否满足某项预期行为或验收条件。**

示例——原文"玩家可以碰牌，碰牌后需要广播给其他玩家，并更新自己的手牌"拆为：

- REQ-001：玩家满足条件时可以碰牌
- REQ-002：碰牌成功后向其他玩家广播
- REQ-003：碰牌成功后更新玩家手牌

边界：不要机械逐句切分，避免大量无业务价值的碎片。
分工：AI 按独立可验证行为提取；**脚本负责结构和完整性校验**。

### 2.2 稳定 ID 策略（P0）

**禁止直接用行号/哈希生成 ID**——PRD 插入内容会导致行号漂移、大批 ID 变化。

采用持久化 ID 映射表（`output/identity-map.json`，跨运行共享）：
- 新需求点通过"来源锚点 + 规范化文本 + 历史匹配"识别是否为已有需求
- 匹配不确定时**标记待确认，禁止自动合并**

### 2.3 指标定义：完成率与通过率必须分开（P0）

```text
检查完成率 = 已完成检查的适用规则点数 / 全部适用规则点数
规则通过率 = 已通过的适用规则点数 / 已完成检查的适用规则点数
```

- 适用性未确认的不得剔除出分母
- **禁止把完成率当通过率**——否则未检查部分被掩盖

## 三、阶段调整（保留并行架构）

| 阶段 | 现有功能 | 调整后 |
|---|---|---|
| 1. 扫描 | 扫描 PRD 和 Rule 文件 | 保留 |
| 2. 需求提取 | 无 | **新增**：提取全部 PRD 需求点 + Rule 原子检查点 |
| 3. 规则检查 | 只输出问题 | 输出每条规则检查点的**覆盖记录 + 问题**（独立分片 + 指纹） |
| 4. 一致性检查 | 发现内部冲突 | 保留，关联需求 ID |
| 5. 汇总去重 | 合并问题 | 合并问题 + **矩阵组装**（确定性） |
| 6. 主题归类 | 按问题归类 | 保留 |
| 7. 报告生成 | 问题报告 | **全量矩阵 + 问题报告**（确定性脚本） |
| 8. 报告审核 | 检查格式 | 增加**需求覆盖、规则覆盖、映射完整性 + 证据校验**（1.4 规则） |
| 9. Dashboard | 问题统计 | 兼容新统计口径（T3）；全量追踪页后置（第二阶段） |

## 四、报告结构

1. 检查概览：需求总数、规则检查点总数、适用数、已完成数、通过数、有问题数、未验证数（完成率与通过率分列）
2. 全量需求追踪矩阵（新增）
3. Rule 覆盖矩阵（新增）
4. 问题清单（保留 P0~P3）
5. 重点问题详情（保留）
6. 检查结论：规则未覆盖、检查失败、待确认项

## 五、验收硬条件

1. 每个被识别的 PRD 原子需求点必须出现在矩阵中（不只展示有问题的）
2. 每个适用 Rule 原子检查点必须有覆盖记录；无对应 PRD 的也必须列出
3. 每条需求-Rule 关联可追溯到源文件、章节或行号
4. 每条映射有明确状态（pass/incomplete/conflict/missing/unverified/na/pending-confirm）
5. 检查组失败 → 对应项标 unverified，不得默认通过
6. 问题实体规范化：一问题一实体，ID 关联，不重复计数
7. report.md、Dashboard、JSON 三者统计一致
8. 完成率与通过率分列展示，不得混用
9. **证据校验 100% 执行**（1.4 六项），不合格记录全部落入 unverified（v4 新增）
10. **每次运行产生独立快照目录 + manifest**（1.2 布局），identity-map 跨运行共享（v4 新增）

## 八、关键注意（实施防坑）

1. 不要用 AI 手写整份全量报告——矩阵上百条必截断；AI 产数据、脚本产报告
2. Rule→PRD 缺口不可武断定缺失——先过范围/强制性过滤，未确认标 pending-confirm
3. 规则原子检查点拆到"单条可判定"粒度（如 UI 基准 `01#3`），避免"一文件一条"失真
4. 与 ui-interaction-prd-extract 同步——其基准已有 `01#N` 条款号体系，rule-catalog 可直接复用
5. 与 rule-checklist 汇报需求联动——RTM 矩阵统计即《需要记录检查过的rule-checklist-分析方案.md》要的"总检查项/通过数/通过率"，落地后合并展示（用 2.3 双指标口径）
6. 证据校验（1.4）与 AI 语义复核是两层防线，不可互替：前者防"引用造假/关联断裂"，后者防"引用真实但结论错误"
