## 五、领导汇报视图调整（新增需求，2026-11-12，基于外部反馈）

**核心意见**：Dashboard 是给领导汇报的，首页不应以“发现了多少问题”为核心，而应先展示“检查规模 → 覆盖 → 风险 → 下一步决策”。两个最值得强调的数字：**363 个原子需求点**（检查规模）与 **1455 个规则检查点**（审计基准规模），应放在最显眼位置而非藏在覆盖清单里。

### 7.7 规则完整通过率（新增首页第一质量指标，2026-11-12 外部反馈定案）

**替换对象**：移除文件级“26.8%（11/41 文件未关联问题）”指标——文件级无关联不代表文件内规则全部通过。

**定义**：规则完整通过率 = 完整通过的适用 Rule 数 ÷ 全部适用 Rule 数（分母=非 na，与 7.2 口径一致）。直接回答领导最关心的问题：“1455 条规则检查，到底符合了多少条？”

**完整通过判定条件（六条全满足）**：
1. 规则属本次 PRD 检查范围
2. 检查任务已成功执行（组失败 → unverified）
3. 关联需求点均已核对
4. 所有必要检查记录判定均为 pass
5. 需求引用/规则来源/检查证据均通过校验（evidenceInvalid 强制 unverified，即使原判定 pass）
6. 无关联的有效未解决问题（P3 优化建议不算）

**规则状态七分类（互斥且穷尽）**：完整通过 / 部分满足（有需求但有缺口）/ 冲突 / 需求缺失 / 未验证 / 待确认 / 不适用（不计入分母）。
关键约束：**一条 Rule 含多条检查记录时，只要存在未验证的必要检查项，整条 Rule 不得判完整通过**。

**实施状态（已落地 rtm-assemble.mjs，run-20261112 重跑验证）**：
- ruleCoverage 条目新增 `evidenceInvalid`、`aggStatus`（七状态聚合结果）字段；stats 新增 `ruleCoverageAgg` 与 `fullPassRate`
- 恒等式自检：total = fullyPassed + partial + conflict + missing + unverified + pendingConfirm + na（不符则结构性报错）
- **真实数据结果：完整通过 437 / 适用 987 = 44.3%**；七状态分布 437+178+53+312+7+0+468=1455，恒等式成立
- 与已检查通过率 44.6%（437/980）差异：分母差 7 条 unverified；核实当前 pass 规则点无一关联 P0~P2 有效问题，两口径在本次数据上一致（完整通过率是显式化与防护，防 evidenceInvalid 规则点误标 pass）
- verify-rtm-assemble.js 新增恒等式与聚合判定断言（19 断言全过）
