# check-spec-coverage 子串假故障——证据 ID 内嵌原子 ID 被误判「串阶段」（S10 假故障）

- 日期：2026-11-18
- 关联：执行文档 §21.8 I11；与 I6（merge 重编号假故障）同族
- 组件：`.opencode-workflows/scripts/check-spec-coverage.mjs`

## 问题现象

S10 收尾闸门（阶段文档 AT-ID 覆盖校验）失败，报 **18 项**「文档混入其他阶段原子（ST-C01）」——18 个非 ST-C01 阶段的规格文档全部被指混入 ST-C01 原子，主流程中断。无一项「缺自身原子」。

## 排查过程

1. 手动重跑闸门命令拿到明细（workflow 抛错不含明细）。
2. 抽查 ST-C02 文档中 `AT-ST-C01-009` 等的上下文：全部出现在**证据 ID**（`SVE-AT-ST-C01-019-04`）或证据表行内。
3. 全量分类：23 份文档中 18 份含跨阶段证据 ID 引用；剔除证据 ID 后另核实 12 处**裸跨阶段提及**，逐一查看上下文——共享证据 atomIds 列举（证据表 `atomIds` 列）、口径一致性交叉引用（「与 AT-ST-C01-015 判 unverified 口径一致」）、证据归属范围说明（「60 条 SVE 的 atomIds 全部落在 ST-C01 系列，无 ST-C10 归属」）——均为合法引用，**无一文档把外阶段原子作为规格主体**。

## 根因

1. **子串假故障（与 merge 重编号假故障同族）**：证据 ID 命名 `SVE-<atomId>-NN` 内嵌原子 ID 子串；校验用 `text.includes(atomId)` 朴素匹配 → 凡引用**共享证据**（atomIds 跨阶段）即被误判「串阶段」。收窄跑（stageIds=ST-C01）下 60 条 SVE 全部归属 ST-C01 原子，其余 22 个阶段文档引用共享证据就必然中招——**收窄越狠误报越多**。
2. 语义过严：原规则「不得出现其他阶段原子 ID」把正文/表格里的合法裸提及也算串阶段；真实意图应是「外阶段原子不得作为规格主体（规格节）」。
3. 反向同源风险：`text.includes(ownAtomId)` 也可能被证据 ID 内嵌子串误当「本阶段原子已覆盖」。

## 解决方案（两向同源修复）

`check-spec-coverage.mjs`：

1. 原子 ID 判定一律基于**裸 ID**：先 `text.replace(/(?:SVE|CLE)-AT-ST-C\d+-\d+-\d+/g, '')` 剔除证据 ID 再匹配（同时消除误判串阶段与误当已覆盖两个方向）；
2. 串阶段判定收紧为**外阶段原子作为规格节标题**：`new RegExp('^#{2,6}\\s*' + id + '(?![0-9])', 'm')`——正文/表格裸提及属合法引用；
3. blocked 窗口判定同样基于裸 ID 文本。

回归：`orchestration.example.mjs` C3 改语义（外阶段原子节标题 → fail）+ 新增 C5（证据 ID 内嵌 + 正文/表格裸提及 → 通过）；11 套 184 用例全绿。

验证：真实 run-001 校验绿——**23 阶段 / 23 文档 / 416 原子（blocked 0 均带「查证未完成」标注）**。

## 预防/注意事项

- **凡「ID 内嵌另一 ID」的命名体系（SVE-<atomId>-NN、CLE-<atomId>-NN），任何 includes 级匹配都是隐患**——要么先剔除长 ID，要么用带边界的正则；本仓库已两次栽在同一族问题上（I6、I11）。
- 「不得出现 X」类闸门先想清楚**语义主体**（覆盖 vs 引用）：引用合法时按结构特征（标题/字段位置）判定，不要按子串存在判定。
- 排查 PowerShell 里 node -e 的正则转义：`\\d` 在单引号字符串里会变成字面 `\d` 字符（不匹配数字）——验证脚本结论（如「裸跨阶段原子=0」）可能因转义失效而失真，关键结论用正则字面量或落盘脚本复核。
