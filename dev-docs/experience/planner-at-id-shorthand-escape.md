# 策划版 AT-ID 缩写标注逃过 prompt 规则、机械校验兜底捕获

## 问题现象

T5.1b 全量重跑（2026-11-14）机械校验失败：`策划版 AT-ID 覆盖缺失 1 个（AI 漏写补充内容）：AT-ST-C09-008`。

人工排查发现策划版 262 行实际有该原子项的标注，但写成了缩写形式：

```
…连乘后的具体数值无法在客户端验证（AT-ST-C09-007、008）
```

一条原文语句对应两个原子项时，agent 没按规则「合并成一条补充行（每个 ID 完整）」而是抄了省略写法「007、008」——校验正则 `/\bAT-ST-C\d{2}-\d{3}\b/g` 只认完整形式，提取不到 008。

## 排查过程

1. 先入为主按「AI 漏写」方向查：搜 ST-C09 章节杠飘语句的补充行——发现 262 行已有该原子项内容，结论「漏写」不成立。
2. 全文搜缩写模式 `、\d{3}）`：命中 3 行，人工确认其中 2 行是牌型名列表（杠上开花、二连杠…）、只有 1 行是真原子 ID 缩写。
3. 全文完整 AT-ID 去重计数 318 = 319 - 1，与缺失 1 个吻合。

## 根因

prompt 规则「每条补充行末尾用括号附原子项 id（AT-ST-Cxx-nnn 形式）」没有显式禁止省略第二个 ID 的前缀——LLM 在多 ID 并列时按中文书写习惯缩写，机械正则不识别缩写形态。**规则约束不到的书写习惯变体，只能靠机械校验兜底捕获**——本次三级闸门（写作 prompt → 泄漏/覆盖正则 → AI 复核）里第二级正则正确拦截，链路有效。

## 解决方案

终产物机械修正：`（AT-ST-C09-007、008）` → `（AT-ST-C09-007、AT-ST-C09-008）`，重跑 build（幂等）通过。

## 预防/注意事项

1. prompt 硬性规则里对「多个 ID 并列」显式写死：每个原子项 ID 都写完整 AT-ST-Cxx-nnn 形式，禁止「、00N」省略前缀。
2. 机械校验（正则口径）是唯一可靠闸门——prompt 规则无论写多细都会被书写习惯绕过，覆盖类校验要按「完整形态」设计而不是「看起来有标注」。
3. 修复此类问题前先全文搜同类缩写模式（避免只修一处漏其他处），并对比「应有个数 - 完整匹配个数」确认缺口一致。
