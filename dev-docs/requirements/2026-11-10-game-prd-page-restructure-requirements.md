# Game PRD 页面结构调整方案

版本：V1.0
日期：2026-11-10
目标文件：`index.html`
调整方式：在现有页面基础上渐进式重构，不重写 GAME-SPEC 数据模型。

> 执行边界约定（人工指示）：P0 先拆工作空间，P1 再调整规格分类，P2 才做裁决选项卡片。不要一次性同时改导航、数据模型和裁决业务逻辑，便于问题定位。

---

## 一、改造目标

当前页面存在的问题：

1. GAME-FR、GAME-RULE、GAME-STATE、GAME-CFG 等规格全部堆积在左侧一个列表中，随着需求增加，导航会越来越长。
2. 裁决工作台与普通 PRD 浏览处于同一个导航体系，交互模式不一致。
3. 裁决问题需要人工选择不同处理方案，目前主要依赖两个下拉框，缺少直观的选项卡片交互。
4. 规格浏览、裁决处理、UI 演示等工作模式之间的职责不够清晰。

本次改造目标：

- 将规格工作台和裁决工作台拆分为两个独立的一级 Tab。
- 规格工作台采用分类导航模式。
- 裁决工作台采用独立的多选项决策交互模式。
- 裁决问题根据各自配置动态展示候选选项。
- 保留现有裁决数据格式、导出能力和业务逻辑。
- 不破坏 UI Demo、Flow、Tests 现有功能。

## 二、整体页面架构

### 2.1 顶部一级 Tab

调整为：

| Tab | 职责 |
|---|---|
| 规格工作台 | GAME-FR、GAME-RULE、GAME-STATE、GAME-CFG、GAME-UI 规格浏览 |
| 裁决工作台 | 原始需求中的未决问题人工裁决 |
| UI Demo | UI 页面演示与交互 |
| Flow | 状态机与流程展示 |
| Tests | 测试用例与测试场景 |

删除原来独立的「裁决」Tab，统一命名为「裁决工作台」。

注意：规格工作台与裁决工作台是两个独立工作空间，不允许将裁决作为 GAME-FR 的二级菜单。

### 2.2 页面布局

保留现有页面顶部游戏信息区域。

不同工作空间允许使用不同的布局，不要求所有 Tab 共用同一种三栏结构。

## 三、规格工作台设计

### 3.1 页面结构

规格工作台采用三栏布局：

左侧：规格分类
中间：当前分类的内容列表
右侧：当前选中项目的详情

左侧分类：

- GAME-FR：功能需求
- GAME-RULE：游戏规则
- GAME-STATE：状态机
- GAME-CFG：数值配置
- GAME-UI：UI 页面与组件

不再将所有需求 ID 直接展开在左侧。

### 3.2 左侧分类交互

点击某个分类：

1. 当前分类高亮。
2. 中间栏切换到该分类内容。
3. 右侧详情展示清空或保留合理的选中状态。
4. 切换分类不影响其他工作空间的状态。

每个分类可以展示数量统计。

例如：

GAME-FR（15）
GAME-RULE（56）
GAME-STATE（8）
GAME-CFG（32）
GAME-UI（5）

以上数字仅为布局示例，实际数量必须从 APP_DATA 动态统计，不得硬编码。

### 3.3 中间栏内容

GAME-FR：

- 搜索需求 ID、名称、描述。
- 按 status 筛选。
- 按 authority 筛选。
- 按来源筛选。
- 需求卡片展示 ID、名称、状态、权限。
- 点击需求后右侧显示详情。

GAME-RULE：

- 按规则分类或章节分组。
- 支持搜索。
- 支持状态与 authority 筛选。
- 展示规则 ID、名称、描述。

GAME-STATE：

- 按状态机或流程分组。
- 展示状态、状态迁移、相关流程。

GAME-CFG：

- 按配置分类或配置组分组。
- 展示配置名称、当前值、类型、默认值和约束（以现有数据字段为准）。
- 适合采用配置表格，而不是普通需求卡片。

GAME-UI：

- 按 UI 页面分组。
- 页面下展示相关组件。
- 支持页面与组件之间的层级浏览。
- 点击页面或组件后展示详情。

注意：五种分类可以使用不同的中间栏渲染器，不要强制复用同一个列表模板。

### 3.4 右侧详情

统一保留右侧详情区域。

根据当前选中对象展示：

- 基础信息。
- 描述。
- 业务规则。
- 前置条件。
- 输入与输出。
- 原始需求来源及引用。
- 依赖关系。
- 关联 UI。
- 关联测试。
- 状态与 authority。

不同类型可以展示不同字段，不存在的字段不显示。

保留原来的需求点击定位、UI 反向追溯能力。

## 四、独立裁决工作台设计

这是本次改造的重点。

### 4.1 设计原则

裁决工作台不复用规格工作台的布局。

它是一个独立的人工决策界面。

核心交互：

选择问题 → 阅读依据 → 选择处理方案 → 补充口径和理由 → 暂存或正式裁决。

建议采用：

顶部：裁决统计与筛选
左侧：待裁决问题列表
中间：问题详情与多选项选择区
右侧：关联需求与影响范围

如果屏幕宽度不足，可以将右侧影响分析放到中间内容下方。

### 4.2 顶部统计区域

动态统计：

- 全部问题数量。
- 待裁决数量。
- 草稿数量。
- 已确认数量。
- 已否决数量。
- 已挂起数量。

统计必须基于 OQ_LIST、DECISIONS 和 DEC_DRAFTS 计算。

特别注意：当前代码中的 DECISIONS 是内存数据，DEC_DRAFTS 来自 APP_DATA，DEC_LOG 来自历史裁决日志。统计时必须正确合并这些来源，避免重复计数。

### 4.3 顶部筛选区域

提供：

- 裁决状态：全部、待裁决、草稿、已确认、已否决、已挂起。
- 严重程度：全部、High、Medium、Low。
- 关联需求：GAME-FR 等需求 ID。
- 关键词：问题 ID、问题描述。

筛选不应清空已编辑的草稿。

### 4.4 左侧问题列表

每条问题展示：

- OQ ID。
- 问题标题或描述摘要。
- severity。
- requirement_id。
- 当前裁决状态。

点击问题后：

1. 当前问题高亮。
2. 中间栏显示该问题的完整内容和候选方案。
3. 右侧显示关联需求和影响分析。
4. 保留当前选中问题状态。

支持按严重程度、状态筛选和排序。

默认优先展示 High 级待裁决问题。

### 4.5 中间裁决区域

这是与普通规格列表最重要的区别。

中间栏不再展示普通需求卡片，而是展示一个问题对应的候选裁决方案。

内容结构：

1. 问题 ID 和严重程度。
2. 问题描述。
3. 原始需求依据。
4. AI 提取出的待确认内容。
5. 候选裁决方案。
6. 自定义修改区域。
7. 裁决理由。

候选方案使用卡片式选择，而不是下拉框。

候选方案支持两种选择模式：

**单选模式**

适用于互斥方案，例如：

- 方案 A：采纳原始需求口径。
- 方案 B：采用修改后的口径。
- 方案 C：否决当前口径。
- 方案 D：挂起待确认。

同一问题只能选择一个方案。

**多选模式**

适用于允许组合的多个独立选项，例如多个规则项可以同时采纳。

允许同时选择多个方案。

必须由问题自身的配置决定使用单选还是多选，不得所有问题默认多选。

选项卡片至少支持：

- 选中状态。
- 方案标题。
- 方案详细描述。
- 方案来源或依据。
- 选择后的补充说明。

对于「人工修改」方案，选择后显示自定义口径输入区域。

对于「挂起」方案，显示挂起原因输入区域。

对于「否决」方案，显示否决理由输入区域。

### 4.6 右侧影响分析区域

展示：

- 关联需求 ID。
- 关联需求名称。
- 关联需求描述。
- 关联 UI。
- 关联测试。
- 可能受影响的规则、状态和配置。
- 历史裁决记录。
- supersedes 关系。

现有代码已经通过 requirement_id 关联需求，继续保留该关系。

影响分析必须以真实关联数据为基础。不能仅根据问题描述猜测已经发生的影响。

对尚未建立关联的数据，显示「待补充关联」，不要伪造。

### 4.7 裁决底部操作栏

提供：

- 暂存草稿。
- 正式裁决。
- 上一个问题。
- 下一个问题。

正式裁决前进行校验：

1. 必须选择有效裁决方案。
2. 修改方案必须填写最终口径。
3. 正式裁决必须填写理由。
4. 多选模式必须满足该问题配置的选择数量约束。
5. 只有明确的人工操作才能生成正式裁决。

正式裁决后：

- 更新问题状态。
- 更新统计数字。
- 更新左侧问题列表徽标。
- 保留当前问题或自动定位下一个待裁决问题。
- 记录 reviewer = human。
- 保留已有 decision_id 和 supersedes 规则。

## 五、裁决选项的数据设计

不要将候选方案直接写死在 HTML 中。

需要支持每个 OQ 自己定义候选选项。

建议在 openQuestions 中增加可选字段 decision_options。

示例：

```json
{
  "id": "OQ-013",
  "requirement_id": "GAME-FR-015",
  "severity": "high",
  "question": "结算公式采用哪种计算口径？",
  "decision_options": {
    "selection_mode": "single",
    "min_selections": 1,
    "max_selections": 1,
    "options": [
      {
        "id": "adopt_original",
        "label": "采纳原始需求",
        "description": "按照原始需求文档中的口径执行",
        "action": "adopted"
      },
      {
        "id": "modify",
        "label": "修改后采纳",
        "description": "人工提供新的结算口径",
        "action": "modified",
        "requires_input": true
      },
      {
        "id": "reject",
        "label": "否决",
        "description": "不采纳当前需求口径",
        "action": "rejected",
        "requires_input": true
      },
      {
        "id": "defer",
        "label": "挂起",
        "description": "等待补充信息后再决定",
        "action": "deferred",
        "requires_input": true
      }
    ]
  }
}
```

以上只是字段结构示例，不能将这些方案直接批量写入所有 OQ。

对于尚未提供候选方案的 OQ：

- 兼容现有裁决方式。
- 可以展示通用裁决选项。
- 不得让 AI 自行编造业务规则作为已确认方案。
- 允许后续人工补充候选方案。

### 5.1 裁决结果兼容

现有 decisions.json 字段必须继续兼容：

- decision_id
- question_id
- decision_status
- outcome
- final_decision
- rationale
- reviewer
- decided_at
- requirement_updates
- affected
- supersedes

新增选项数据可以增加字段，例如：

```json
{
  "selected_option_ids": ["adopt_original"],
  "selection_mode": "single",
  "custom_decision": null
}
```

新增字段不能替代原来的 outcome 和 decision_status。

需要保证现有 apply-decisions.mjs 能正常处理旧格式和新格式。

如果下游暂时不支持新字段，应先保持旧字段作为唯一正式裁决接口，新字段仅作为辅助信息，不得擅自改变 apply-decisions 的契约。

## 六、代码改造范围

当前 index.html 中需要重点调整以下部分。

### 6.1 顶部导航

当前：

```html
<button data-tab="prd">PRD</button>
<button data-tab="ui">UI Demo</button>
<button data-tab="flow">Flow</button>
<button data-tab="tests">Tests</button>
<button data-tab="decision">裁决</button>
```

调整为：

```html
<button data-tab="spec">规格工作台</button>
<button data-tab="decision">裁决工作台</button>
<button data-tab="ui">UI Demo</button>
<button data-tab="flow">Flow</button>
<button data-tab="tests">Tests</button>
```

### 6.2 规格工作台

调整：

- GROUPS：从简单的分组过滤器升级为规格分类配置。
- renderNav()：改成规格分类导航，不再展开全部需求。
- renderPrd()：拆分为规格工作台入口及不同分类渲染器。
- showRequirement()：支持根据需求类型切换规格分类。
- showDetail()：继续承担右侧详情展示。

建议增加：

```js
const SPEC_CATEGORIES = [
  { id: "GAME-FR", label: "功能需求" },
  { id: "GAME-RULE", label: "游戏规则" },
  { id: "GAME-STATE", label: "状态机" },
  { id: "GAME-CFG", label: "数值配置" },
  { id: "GAME-UI", label: "UI 页面与组件" }
];
```

注意：以上是导航配置，不要将 ID 前缀直接当成所有数据的真实 type。应该根据现有 APP_DATA 的实际字段建立分类映射。

### 6.3 工作空间切换

当前：

```js
let currentTab = "prd";

function switchTab(tab, after) {
  // ...
}
```

改成明确的工作空间状态：

```js
let currentWorkspace = "spec";

let specState = {
  category: "GAME-FR",
  selectedId: null
};

let decisionState = {
  selectedOqId: null,
  statusFilter: "all",
  severityFilter: "all",
  keyword: ""
};
```

规格工作台和裁决工作台各自管理自己的状态。

切换 Tab 不得意外丢失当前编辑中的裁决内容。

### 6.4 裁决工作台

当前：

- renderDecision()
- selectOq()
- saveDecision()
- exportDecisions()

需要重构为：

- renderDecisionWorkbench()
- renderDecisionList()
- renderDecisionQuestion()
- renderDecisionOptions()
- renderDecisionImpact()
- saveDecision()
- exportDecisions()

其中保存与导出业务尽可能复用现有实现。

### 6.5 统一状态管理

需要处理：

- 左侧问题状态徽标更新。
- 正式裁决后的进度统计更新。
- 筛选状态变化。
- 切换问题时草稿恢复。
- 切换工作空间时保留未提交内容。
- 正式裁决后重新选择问题时正确加载裁决结果。

不能只修改 DOM 显示而不更新真实状态。

## 八、执行阶段

### P0：工作空间拆分

交付：

- 顶部独立一级 Tab。
- 规格工作台独立布局。
- 裁决工作台独立布局。
- 两套工作空间状态隔离。
- 删除左侧原有全部需求长列表。

验收：

- 点击规格工作台，只出现规格分类导航。
- 点击裁决工作台，完全切换成裁决专属界面。
- 裁决工作台不出现 GAME-FR、GAME-RULE 等规格分类导航。

### P1：规格工作台分类化

交付：

- GAME-FR、GAME-RULE、GAME-STATE、GAME-CFG、GAME-UI 五类导航。
- 中间栏按分类渲染。
- 右侧统一详情。
- GAME-CFG 使用配置型展示。
- GAME-UI 按页面和组件分组。
- 需求搜索、筛选、关联跳转。

验收：

- 五类数据均能正常显示。
- 点击需求后右侧正确显示详情。
- 原来的 UI 定位和反向追溯正常。

### P2：裁决工作台交互重构

交付：

- 顶部裁决统计。
- 问题筛选。
- 左侧 OQ 列表。
- 中间候选方案卡片。
- 单选和多选模式。
- 自定义口径输入。
- 右侧影响分析。
- 底部操作栏。

验收：

- 每个 OQ 可以独立配置候选选项。
- 单选、多选约束正确。
- 修改、否决、挂起均有相应输入区域。
- 正式裁决校验有效。
- 切换问题不会丢失草稿。

### P3：裁决数据兼容与回归

交付：

- decisions.json 兼容。
- 旧版裁决记录兼容。
- decision_id 和 supersedes 正确。
- 正式裁决导出。
- apply-decisions.mjs 兼容性验证。
- 刷新丢失风险有明确提示。

验收：

- 旧版数据能够正常加载。
- 新版裁决能够正常导出。
- 导出结果可以通过 apply-decisions.mjs --dry-run。
- 正式裁决状态与导出数据一致。
