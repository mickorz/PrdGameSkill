- **日期**：2026-11-14
- **状态**：已确认，第一阶段（T0.1~T0.4）执行中
- **前置**：OSG-W3（策划视图分离）产物已就绪——`spec-workflow/output-spec/2026-11-14/1-spec/`（319 原子、schema_version=2、difference_stats：consistent 65 / partial 64 / conflict 2 / unverified 188、trace_index.json、策划版文档）
- **需求来源**：2026-11-14 外部评审结论（本文档固化）

## 1. 核心目标

不是增加更多「待确认」记录，而是让 Workflow 能准确回答三个问题：

1. 当前需求究竟由客户端、公共服务端还是杭州麻将服务端负责？
2. 查到的代码是否真的在「杭州麻将好友房」配置下生效？
3. 现有 `difference` 结论，哪些是真正的冲突，哪些只是证据不充分？

**架构决策**：保留现有四阶段 output-spec-generate Workflow，不重新跑客户端查证，新增独立的服务端补证与差异复核流程（`server-rule-verify/`）。

## 2. 三项改造

### 2.1 L7 修复：把「待确认」拆成四种含义

当前策划版主要依据 `notes`/`uiInteraction`/`verdict` 编写，而 `notes` 同时混装三种含义（服务端职责规则 / 客户端未找到 / 真实冲突），不能共用一种「待确认」口径。新增结构化分类：

| 分类 | 含义 | 策划版表达 |
|---|---|---|
| `verified` | 已有足够证据验证规则 | 不生成待确认 |
| `verification_required` | 缺少必要证据 | 规则待验证 |
| `decision_required` | 已发现明确冲突 | 待策划裁决 |
| `not_applicable` | 证据属于其他玩法 | 不纳入当前玩法冲突 |

L7 的根本修复：**策划版依据结构化判定结果生成，不再要求 LLM 猜测 `notes` 是否代表差异。**

### 2.2 新增玩法配置作用域（scope）

服务端工程存在公共层（common_game）与玩法层（hzmj_server），**不能假定公共实现必然在好友房生效**。每条服务端证据附带：

```json
{
  "atomId": "AT-ST-C02-004",
  "scope": {
    "game": "hzmj",
    "roomType": "friend",
    "applicability": "unknown",
    "configVerified": false,
    "callPathVerified": false,
    "evidence": []
  }
}
```

`applicability` 四值：`active`（已验证当前玩法配置下生效）/ `conditional`（满足特定配置条件才生效）/ `inactive`（已验证不生效）/ `unknown`（尚无法确认）。

只有查到函数还不够，至少需证明规则选择条件与调用路径。典型样例：客户端支持白板财神与翻财神，若服务端好友房固定白板财神，通用翻财神代码不构成冲突；反之若允许翻财神而 PRD 固定白板，需追查配置范围，必要时标 conflict。

### 2.3 Difference 二次质量检查

当前 v2 全量：consistent 65 / partial 64 / conflict 2 / unverified 188。复核优先级：全部 2 个冲突 → 64 个 partial → 按业务风险补查 188 个 unverified。

复核规则（五条）：

1. 找到直接实现证据，不等于规则一致。
2. 缺少服务端证据，不等于规则冲突。
3. 通用能力存在，不等于当前玩法启用。
4. 客户端视觉冲突即使服务端规则正确，仍可能是真实 UI 冲突。
5. 任何状态变更保存原始 `difference`、新状态、理由与证据，不直接覆盖历史事实。

复核结果独立落 `difference-review.json`（与 trace_index 的 atomId 对齐），复核批准后才合并进新索引版本。

## 5. 第一阶段任务（本轮执行范围）

- **T0.1 服务端结构扫描**（只读）：代码语言、目录结构、核心类与入口；两模块依赖与调用关系；好友房配置入口；定庄轮庄/财神/吃碰杠优先级规则入口；规则如何经配置、继承或调用链生效。**不得因找到同名函数就认定其在好友房生效。**
- **T0.2 原子需求匹配**：复用现有 Atom ID 不重新拆解；优先匹配 ST-C01 / ST-C02 / ST-C04；保存代码路径、定位、有效配置条件、调用链及无法验证部分。
- **T0.3 L7 与 difference 分类设计**：设计独立 Sidecar（server-evidence.json / scope-index.json / difference-review.json）；区分已验证 / 待验证 / 冲突待裁决 / 其他玩法不适用；保留原 difference、verdict 与客户端证据不覆盖。
- **T0.4 局部验收**：服务端证据真实存在；配置与调用链可核；通用能力不自动判好友房冲突；缺服务端证据不自动产生冲突；真实客户端视觉冲突不被错误消除；输出复核前后 difference 对比。

**交付物**：服务端结构与职责调查报告、玩法配置作用域设计说明、L7 分类与二次检查方案、三个 Stage 的服务端证据映射样本、OSG-W4 后续执行计划。
