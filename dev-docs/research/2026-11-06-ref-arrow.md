## 一、项目概况

Arrow 是一款开源的"游戏叙事设计工具"（The Game Narrative Design Tool），定位类似 Twine / articy:draft 的轻量开源替代品。核心形态：

- **编辑器**：Godot 4.4 工程（`project.godot`，GL Compatibility 渲染），可视化节点图编辑器。每个节点类型是 `nodes/<type>/` 下的一个文件夹（含 node 场景、inspector 面板、console 试玩视图、图标、翻译），由 `scripts/core/node_types_handler.gd` 在启动时从 `res://nodes` 目录动态发现并加载——节点类型本质上是"插件式"的。
- **运行时（Runtime）**：一套与编辑器完全独立的纯 JS 解释器，位于 `runtimes/html-js/`（约 4500 行，无任何构建依赖、无第三方库）。编辑器用它做"一键导出可玩 HTML"。
- **内置节点类型 19 种**：entry、content、dialog、monolog、condition、variable_update、tag_edit/tag_match/tag_pass、randomizer、generator、sequencer、hub、jump、interaction、user_input、marker、frame、macro_use，覆盖逻辑分支、变量、角色标签、随机、交互输入等叙事所需原语。

架构上的关键决策：**编辑器与运行时之间只有一个 JSON 文档格式作为契约**。编辑器产出 JSON，运行时解释 JSON，两者互不依赖。

## 二、固定问题逐条回答

### 问题 1：节点（Node）运行时如何求值执行？

**结论：解释器模式，`play_node` 驱动的单步推进状态机；求值全部数据驱动，不使用 eval。**

核心流程（`runtimes/html-js/arrow.js`）：

1. 页面 `load` 后进入 `runtime()` 函数（arrow.js 底部）：校验 `PROJECT` 常量（`validate_project_data()`，检查 title/entry/meta/resources 及各数据集必填字段），初始化全局变量与角色，然后从 `PROJECT.entry` 节点开始调用 `play_node()`。
2. `play_node(node_id)`（arrow.js 约 330 行附近）：
   - `get_resource_by_id(node_id)` 查节点资源，`get_node_map_by_id()` 查它在所属 scene 的 `map` 中的图数据；
   - 按 `node_resource.type` 从 `NODE_CLASSES_BY_TYPE` 查表（arrow.js 顶部，19 个类型到类的映射）实例化对应节点类；
   - 压入 `OPEN_NODES_BY_ORDER`（全局播放历史栈，供回溯）；
   - 调用 `instance.proceed()` 触发该节点的"自动播放或等待交互"。
3. **节点类的统一约定接口**（每个模块都实现同一套方法）：
   - `proceed()`：入口。若节点可自动推进（`_ALLOW_AUTO_PLAY = true`，arrow.js 顶部常量）且图上标记 `skip == true` 则调 `skip_play()`，否则自动求值/等待用户点击；
   - `play_forward_from(slot_idx)`：沿槽位找下一条连接并递归 `play_node(next.id)`；槽位无出边时调 `handle_status(END_EDGE)`；
   - `skip_play()` / `step_back()` / `set_view_played()`：视图与回溯辅助。
4. **连接（边）的数据格式**：scene 的 `map.io` 是 `[from_id, from_slot, to_id, to_slot]` 四元组数组。`runtimes/html-js/modules/shared.js` 的 `remap_connections_for_slots()` 把出边按槽位号重映射为 `slots_map[slot_idx] = {id, slot}`，节点模块据此寻路。
5. **求值无 eval，纯查表**：以 `modules/condition.js` 为例，条件语句序列化为 `{variable, operator, with:[parameter_mode, value]}` 结构；`ConditionStatement.evaluators` 按 `str/num/bool` 三类各注册一组运算符函数（str 支持 rgx 正则、ct/cts 包含、eql/lng/shr 长度比较、bgn/end 前后缀；num 支持 eq/nq/gt/gte/ls/lse）。求值失败一律兜底为 `false` 并告警，不中断播放。
6. **自动推进与清屏**：entry/content/condition 等无交互节点会自动连放到下一个需要用户输入的节点；`modules/content.js` 支持 `_ALLOW_CLEARANCE`（arrow.js 常量）在新内容出现时清掉旧节点（`clear_up()`）。
7. **宏（macro_use）**：全局变量 `OPEN_MACRO` 持有当前宏上下文。`play_node` 中若新节点属于宏（`OPEN_MACRO.owns_node()`），实例不挂主视图而是挂进宏的容器；宏内节点走到末边时由 `handle_status(END_EDGE)` 判断返回主场景继续 `play_self_forward()`（`modules/macro_use.js`）。
8. **回溯（Back 按钮）**：`play_back(steps)`（arrow.js）从 `OPEN_NODES_BY_ORDER` 弹栈并移除 DOM 元素，然后对上一个节点重新调 `step_back()` 使其可再次交互。注意这是 **UI 层面的"倒带重放"，不是状态快照回滚**——变量值不会随回退恢复（`variable_update.js` 在重播时会在节点被重复触发前记录并恢复自身写入的旧值，属于局部补偿，非全局快照）。
9. **编辑器侧同构实现**：编辑器内试玩（`scripts/editor/panels/console.gd` + 各节点类型目录下的 console 视图脚本）与 JS 运行时是两套平行实现，共享同一 JSON 契约，保证"编辑器里试玩"与"导出 HTML 试玩"行为一致。

### 问题 2：变量与状态如何存储？

**结论：全部运行时状态是解释器里的几个全局普通对象 + DOM data 属性镜像；无持久化、无外部存储。**

（均在 `runtimes/html-js/arrow.js`）

1. **变量表 `VARS = {}`**：运行时全局对象。启动时 `sort_global_variables()` 从 `PROJECT.resources.variables` 初始化：每个变量 `{name, type, init}`，运行时值拷贝到 `value = init`。类型系统极简，仅 `num / str / bool` 三种（`_SUPPORTED_VARIABLE_TYPES`）。
2. **写入带类型检查**：`update_global_variable_by_id(var_id, new_value)` 强校验新值类型与声明类型一致（num 必须 `Number.isInteger`），不一致直接 `throw`，属于"快速失败"设计。另提供按名字查找写入的 `update_global_variable_by_name`（线性遍历，变量表小无所谓）。
3. **角色表 `CHARS = {}`**：`PROJECT.resources.characters` 初始化，每个角色 `{name, color, tags{}}`；`tag_edit` 节点通过 `update_global_characters_tags()` 增删改角色标签（值为 null 即删除）。
4. **文本插值 `exposure(text)`**：播放文本时把 `{var_name}` 与 `{角色名.标签}` 占位符用 `replaceAll` 替换为当前值——模板渲染就是简单字符串替换，无表达式求值能力。
5. **状态镜像到 DOM**：每次变量更新同步写 `#console` 元素的 `data-{变量名}` 属性（`refresh_console_attribute_of()`），节点容器 `#content` 写 `data-open-nodes`。这让 CSS 可以按状态换样式（如 `#console[data-hp="0"]`），运行时状态对样式层完全可观测。
6. **播放历史 `OPEN_NODES_BY_ORDER`**：数组栈，记录已播节点 `{id, resource, instance, wrapper}`，仅服务于 Back 回溯和清屏，不是存档。
7. **无持久化**：运行时不写 localStorage（唯一例外是深色模式偏好 `window.localStorage['_arrow_runtime_darkmode']`），刷新页面即从头开始。变量初始值只来自 JSON 的 `init` 字段。
8. **编辑器侧持久化**：项目以 `.arrow`（JSON）文件保存（`scripts/core/project_management.gd`），`scripts/shared/shared_helpers.gd` 提供读写与 JSON 解析；变量/角色的编辑 UI 在 `scripts/editor/panels/inspector_variables.gd`、`inspector_characters.gd`。

### 问题 3：HTML Export 打包了什么，产物能否离线运行？

**结论：打包为单文件 HTML（运行时代码 + 内联 CSS/JS + 项目 JSON 内嵌），产物完全离线可用，零依赖、零网络请求。**

导出链路（编辑器侧，全部同步字符串处理，无构建工具）：

1. **模板源**：`runtimes/html-js/index.html` 是入口模板，`<head>` 中 `<!-- @inline -->` 到 `<!-- @inline-end -->` 之间列出全部 JS 模块（shared、19 个节点模块、arrow.js）与 `arrow.css` 的外链引用。
2. **模板构建**：`scripts/shared/shared_helpers.gd` 的 `read_html_head_imports()` / `inline_html_head_imports()`：按 `@inline` 标记定位区间，正则抓出 `<script src>` 与 `<link href>`，逐个读文件内容替换为内联的 `<style>` / `<script>` 块。结果写入单文件模板 `runtimes/html-js.arrow-runtime`（`scripts/settings.gd` 中 `HTML_JS_SINGLE_FILE_TEMPLATE_PATH`）。是否重建由文件修改时间判断（`is_html_js_runtime_modified()`，`scripts/core/project_management.gd`），支持"改了运行时源码后自动重建模板"（Hybrid 定制流）。
3. **数据净化**：`revise_play_ready(project)`（project_management.gd）深拷贝项目字典，按 `scripts/settings.gd` 的 `PURGE_DEVELOPMENT_DATA_FROM_PLAYABLE` 配置删除开发期字段：meta 中的 `offline/remote/last_save/authors`，nodes 中的 `notes` 等——导出的 JSON 只含运行所需数据。
4. **占位符替换**：`tag_replacements_from()` 生成替换表：`{{project_title}}`、`{/*project_json*/}`（净化后的项目 JSON 整体嵌入 `project.js` 的 `const PROJECT = {...};`）、`{{arrow_version}}` 等；`save_from_template_file()` 逐行读模板做字符串替换写出最终 `.html`（project_management.gd 的 `save_playable_html()`）。
5. **产物构成**：一个 `.html` 文件 = 完整 HTML 骨架 + 全部内联 JS（解释器 + 19 个节点模块）+ 内联 CSS + `const PROJECT = {…项目 JSON…}`。运行时是纯 DOM 操作（`document.getElementById("console")` 等），不 fetch 任何外部资源，无图片资源依赖（字体走系统字体，见 readme 的 PWA 限制说明）。
6. **离线验证依据**：`runtimes/html-js/readme.md` 明确说明 Quick Export 产出 "a single `.html` document ... ready to play"，`file://` 协议直接打开即可（无模块加载、无 CORS 需求，全部内联）。产物未压缩未混淆，可直接手工二次编辑。

## 三、对 Interactive Game PRD 项目（游戏玩法模拟器）的可借鉴点

结合本项目目标（用 PRD 文档驱动的游戏玩法模拟器），Arrow 有以下可直接吸收的设计：

1. **"文档格式作为编辑器与运行时的唯一契约"**：编辑器只产 JSON，运行时只读 JSON。Interactive Game PRD 可照此把"PRD 文档（含玩法节点图）"编译/净化成一个自包含 JSON，模拟器运行时只依赖该 JSON——编辑工具（无论 Markdown 还是 GUI）与模拟器彻底解耦。
2. **导出净化（purge）机制**：`revise_play_ready` 的做法值得照抄——面向模拟器的导出剥离编辑期元数据（作者、备注、评审记录），产物更小且不泄露内部信息。
3. **单文件 HTML 导出**：`@inline` 标记 + 逐个内联 + 占位符替换，整个"打包器"不到 100 行 GDScript（shared_helpers.gd + project_management.gd 相关函数），无需引入打包工具链。产物"下载即玩、离线可用"，非常适合 PRD 评审场景：策划/投资人拿到一个 html 文件即可体验玩法原型。
4. **节点模块的统一接口约定**：`proceed / play_forward_from / skip_play / step_back / get_element` 五件套，每个节点类型一个自包含模块，注册表查表实例化。这是节点系统可扩展性的最小实现，模拟器的玩法节点（如"掷骰""资源变更""分支""随机事件"）可按同样约定组织。
5. **数据驱动求值，禁用 eval**：条件 = `{变量, 运算符, 右值/右变量}` 结构 + 按类型的运算符函数表。安全、可序列化、可跨语言实现（GDScript/JS 各一份同构），还便于做静态校验（编辑期即可发现引用了不存在的变量）。
6. **极简强类型变量系统**：`num/str/bool` 三型 + 写入时类型强校验 + 快速失败 throw。对 PRD 模拟器而言够用且防止静默类型污染；PRD 中的游戏状态（回合数、资源量、开关标记）都可映射。
7. **状态镜像到 DOM data 属性**：运行时状态变化同步写 DOM 属性，CSS 按状态切样式。模拟器可用同样技巧零成本实现"状态可视化/调试视图"。
8. **交互自动推进 + Back 栈**：无交互节点自动连放到下一个决策点，符合"模拟器自动跑、人在分支点介入"的体验；`OPEN_NODES_BY_ORDER` 回溯栈让用户可反悔重来。注意其局限：回溯不回滚全局变量，若模拟器需要"真正的时光倒流"，需要在借鉴时补状态快照（在进入每个节点前深拷贝 VARS 入栈即可，成本很低）。

## 四、三档结论

| 档位 | 内容 | 理由 |
|------|------|------|
| **复用代码** | 暂无直接复用项 | Arrow 运行时是 GD 风格过程式 JS + DOM 直操作，与本项目技术栈（待定，若为 Web 则框架化程度更高）不匹配；整体引入会拖入 19 种叙事向节点，其中多数（dialog/monolog/BBCode 排版等）与玩法模拟器无关。若未来决定采用纯静态 HTML 单文件产物形态，可参考其 `index.html` 模板结构与 `@inline` 内联约定自行实现（实现成本极低，见上文不到 100 行的参照）。 |
| **借鉴思想** | ① JSON 单契约解耦编辑器与运行时；② 节点模块统一接口 + 查表实例化；③ 数据驱动条件求值（禁 eval）；④ 三型强校验变量系统；⑤ 导出净化 purge；⑥ 单文件离线 HTML 产物；⑦ 状态镜像 DOM data 属性；⑧ 自动推进 + 回溯栈（需补状态快照） | 这八点是 Arrow 架构中最经得起推敲的部分，全部为通用设计模式，实现成本低、收益直接对应模拟器核心需求（PRD 驱动、可分享、可试玩）。MIT 协议允许借鉴。 |
| **不采用** | ① 叙事向节点全集（dialog/monolog/sequencer 等 19 种照搬）；② BBCode 混合样式体系；③ 回溯不回滚状态的"倒带"设计；④ 编辑器侧 Godot 工程 | 模拟器核心是玩法数值与规则推演，不是对话树排版；回溯不回滚变量在"试玩 PRD"场景下会造成状态错乱（用户退回重选分支但数值已变），模拟器必须做快照式回滚；Godot 编辑器与本项目技术路线无关，仅作方法论参考。 |
