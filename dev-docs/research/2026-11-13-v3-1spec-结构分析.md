## 2. 数据层级模型

```
Stage（阶段 ×14）
  └─ Feature Point（功能点 ×73，FP-ST-xxx-nnn）
       └─ Atom（原子项 ×375，AT-ST-xxx-nnn，全局连续编号）
            └─ Source Unit（代码符号单元 SRC-0000000000000xxx，2693 个，其中 396 个被原子项引用）
```

- 编号规则：功能点 `FP-ST-001-001`、原子项 `AT-ST-001-001`；原子项 ID 在阶段内连续、跨阶段不重置（ST-011 的原子项编到 AT-ST-011-040）。
- 每条原子项引用 1 个 SRC 单元并附源码行摘录；未引用的 2297 个单元统一登记为 `non_requirement`（实现载体，不是独立业务需求）。
- 来源：线上杭麻服务端反推（`server/Logic/mahjong_server/src/game_hzmj/`），覆盖 6 个变体目录：common_game（1952 单元，公共层）、hzmj_server（124）、xiaoshanmj_server（230）、tonglumj_server（166）、chunanmj_server（118）、hzmj2r_server（103）。
- 符号类型分布：func 2424 / class 161 / field 78 / macro 22 / enum_item 8。

### 3.2 `stages/spec_stage_ST-*.md`（阶段文档模板）

每个文件统一结构：

```
# {阶段名}
## 0. 阶段                    ← 阶段表行：入口/进入条件/退出条件/跳过失败
## 术语与单位（有则填）
## 跨切面行为（无原子也列）
## FP-ST-xxx-nnn {功能点名}
  - 主描述 / 范围与边界 / 总体协作
  ### 原子项
  #### AT-ST-xxx-nnn {原子名}
    - 规则说明 / 触发条件 / 配置影响 / 客户端交互 / 限制与禁止 / 异常与边界 / 验收
    - 职责域 / 职责依据 / 服务端职责 / 客户端职责 / 协作边界

```

其中 **`客户端交互`、`客户端职责`、`协作边界` 三个字段是阶段文档侧的 UI 交互落点**（对应 JSON 侧的 `client_interaction`）。当前 `客户端职责` 普遍写"本次仅还原服务端；客户端消费 MsgXXX 展示"。

## 5. UI 交互补充的接入点（本分析的核心结论）

### 5.1 既有挂点已经预留

结构设计时就为 UI 交互留了字段，不需要改 schema：

1. **JSON 侧**：`feature_index.json` 每条原子项的 `client_interaction` 字段（现 353/375 为空字符串）。
2. **MD 侧**：阶段文档每个原子项的 `客户端交互` / `客户端职责` / `协作边界` 三个列表字段，以及功能点头部的 `总体协作`。

### 5.2 已填 22 条的格式规律（ST-002 全阶段已填，可直接当样板）

ST-002 的 22 条 `client_interaction` 全部是**协议字段引用格式**，两种写法：

- 字段级：`MsgJuData.zhuang`、`MsgJuData.lian_zhuang`、`MsgJuData.banker_level`（消息名.字段名）
- 消息级：`MsgJuData(1405) 全桌广播`、`无独立交互，结果经 MsgJuData(1405) 下发`
- 无交互：`无（字段不进 MsgJuData）`

即当前约定是**最小口径**：只写"该规则对应哪条下发给客户端的消息/字段"，不描述 UI 表现（弹什么窗、点什么按钮、播什么动画）。

### 5.3 补充 UI 交互时需要区分的两个层次

| 层次 | 内容 | 落点字段 | 现状 |
| --- | --- | --- | --- |
| L1 协议对接层 | 原子项 → 下发消息/字段/触发时机 | `client_interaction`（沿用 ST-002 格式，把 353 条空缺补齐） | 22/375 |
| L2 UI 交互层 | 消息/操作 → 界面表现（提示弹窗、按钮可用态、动画、倒计时、面板刷新） | 需新增字段或并行文档，按仓库 issue 维度约定应归入「UI 交互」维度 | 0 |

L2 与本仓库既有的 UI 交互工作流衔接：`ui-interaction-prd-extract` 产出「UI 交互」维度问题，`game-prd-check` 产出「功能规则」维度（见 `dev-docs/research/ui-interaction-prd-extract-流程分析.md`）。本 1-spec 是纯服务端反推（owner 全部 server、校验口径"客户端职责=消费下发"），L2 层需要客户端侧基准（截图/客户端代码）才能填，不能凭服务端代码杜撰。

### 5.4 建议的补充路径

1. **先补 L1**：按第 4 节的"涉及协议消息"列逐阶段把 353 条空缺 `client_interaction` 补成 ST-002 格式；ST-002 样板已验证格式可行。高频消息（MsgJuData/MsgPower/MsgResultHu/MsgJoker/MsgRelinkOnAction）覆盖的原子项可批量推导。
2. **再做 L2**：L1 补完后，以协议消息为轴（48 种消息 → 每种消息对应的界面表现清单）建 UI 交互并行文档，不侵入 1-spec 既有结构；维度口径沿用「UI 交互」。
3. **重连消息单列**：7 种 MsgRelinkOn* 跨阶段复用（ST-012 集中），UI 交互层建议按"重连快照"独立成组而不是散在各阶段。
4. 注意 `spec_check_report.md` 的「端侧职责」维度口径是"仅还原服务端"，L1/L2 补充后需要重跑校验或同步修订该报告口径，避免报告与数据不一致。
