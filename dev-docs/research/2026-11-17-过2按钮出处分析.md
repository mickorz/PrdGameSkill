# 「过2」按钮出处分析（客户端 + FairyGUI）

> 分析对象：`spec-workflow/output-spec/核心流程杭州麻将好友房AI-策划版.md`
> 分析日期：2026-11-17
> 关键条目：「【过】与「过2」同时出现时最右侧是「过2」」「过上行放弃；过2只在本地收起按钮并清掉本次压暗，再按禁手重新压暗，不上行」

## 结论

PRD 里的「过2」来自**客户端杭州麻将代码**与 **FairyGUI `box_hzmj_main` 包**，三处证据链：

1. 客户端权限位掩码定义了两个「过」位（`POWER_ID_CANCEL_C` / `POWER_ID_CANCEL_S`）；
2. 客户端视图层把两个位分别绑到「过」「过2」两个按钮，行为一上行一本地；
3. FairyGUI `Handler.xml` 中「过2」（x=2528）排在「过」（x=2338）右侧，是「最右侧是过2」的直接依据。

代码快照位置：`source-code/client/`（PrdGameSkill 仓库内）。

## 证据链

操作按钮按 x 坐标从左到右固定排布，同属 group `n52_ev1d`，由控制器 `C_BtnState` page=2（碰杠胡页）控制显隐：

| 按钮 | 组件 id | x 坐标 |
|---|---|---|
| 吃 KW_BTN_Chi | n125_qy3a | 1250 |
| 碰 KW_BTN_Peng | n80_gv5d | 1440 |
| 杠 KW_BTN_Gang | n81_gv5d | 1630 |
| 胡 KW_BTN_Hu | n82_gv5d | 1820 |
| 报听 KW_BTN_Bao_Ting | n124_ptn1 | 2148 |

| **过2 KW_BTN_Guo2** | n117_b2ev | **2528（最右）** |

两个过按钮都是同一个 `component/EffectBtn.xml`（150×150，内含 `KW_Ani` 主动画 + `KW_AniLight` 高亮动画两个 Loader3D，默认皮肤 `quxiao`，代码运行时替换为 `guo`）。因为共用同一皮肤动画，PRD 写「过和过2都显示『过』，玩家无法从外观区分」。

**x=2528 > x=2338**，即「过2」位于「过」右侧 190px 处 —— PRD「【过】与「过2」同时出现时最右侧是「过2」」的直接布局依据。

## 命名陷阱：枚举注释编号与按钮名相反

枚举注释的「过 1/过 2」编号与 UI 按钮名的「过/过2」**语义相反**：

| 口径 | 本地过（不上行） | 上行过（需上报） |
|---|---|---|
| 枚举注释（BoxMahDefine.ts） | 过 1 = CANCEL_C | 过 2 = CANCEL_S |
| 按钮实际绑定（BoxHzmjMainView.ts） | **过2** = CANCEL_C | **过** = CANCEL_S |

PRD 的行为描述（「过上行放弃；过2只在本地收起」）与**按钮绑定实现一致**，说明 PRD 取的是按钮名口径（`KW_BTN_Guo2` / `showGuo2` / `onBtnGuo2`），不是枚举注释的编号口径；`onBtnGuo2` 处较新的注释也确认了这个对应关系。

**写 PRD / 读代码时若按枚举注释口径理解，会把两个过的行为写反。**

## 设计意图分析：为什么要有两个过

### 一句话本质

**分界线 = 服务端是否在阻塞等待这个表态。** 需要服务端裁决才能推进牌局的放弃必须上行（过）；服务端不等待、出牌即隐含放弃的，本地收尾即可（过2）。

### 过（CANCEL_S，上行）：同步裁决的放弃

服务端下发 `MsgPower` 时带 `askid`（裁决会话号，`GamePowerCmd.ts` L55 `setPowerAskid`）。对他人弃牌的吃/碰/直杠/点炮胡是**同步询问**：服务端必须收齐所有有资格玩家的表态，才能按优先级（胡>碰杠>吃，同级按座位号）裁决。PRD 的「近者放弃后远者仍可胡」「低优先级先提交时先等更高优先级表态」都以「每家明确表态」为输入，所以放弃必须 `sendCancel()` 带 askid 回包登记。

### 过2（CANCEL_C，本地）：同回合可选操作的收尾

典型场景是暗杠/碰后加杠提示（`onBtnGuo2` 注释「暗杠/碰吃等同回合场景」）。这类操作主动权完全在自己手里，服务端等的只是「出牌或杠」二选一——**出牌消息本身就隐含放弃杠**，服务端没有阻塞等待「放弃暗杠」声明，上行过包是纯冗余。

按钮仍存在的意义是**防呆**（`BoxHzmjMainView.ts` L1445-1461）：有吃碰杠胡按钮时直接点牌会被拦、弹「点"过"才能出牌」。手牌置灰提示可杠时，若点牌直接出出去，想杠的玩家会误丢杠权，强制显式确认；确认动作只需本地收起按钮（收按钮、清压暗、按禁手重新压暗），不打扰服务端。

### 设计收益

1. **省包省延迟**：暗杠提示高频出现，过2 点击零 RTT 即生效。
2. **服务端状态机简化**：无需处理、存储「同回合放弃暗杠」消息。
3. **避免副作用污染**：上行过会登记进 askid 裁决并带规则后果（如「放弃杠后同一次操作机会内不再出现【杠】」）；过2 不进任何裁决，误点不会经服务端丢权——外观相同的两个按钮里，误点过2 反而是安全的那个。
4. **状态一致性补偿**：过2 不上行即服务端不知情，故 `onBtnGuo2` 内做 `_clearPowerHandGray()` + `onPlayLmtsUpdate()`，本地重新按禁手规则压暗，保证 UI 仍反映服务端真实限制。

### 外观相同与过2在最右的原因

- **外观相同**：玩家心智模型只需一个「过」= 放弃当前待办，上行与否是纯技术实现，对玩家透明；两个过的可见效果一致（按钮收起、手牌恢复可打），不区分即无学习成本。
- **最右**：`Handler.xml` 静态坐标按操作优先级从左到右（吃 1250 → 碰 1440 → 杠 1630 → 胡 1820 → 报听 2148 → 过 2338），过2 作为同类第二个变体追加在过右侧（2528），放弃类操作排最末位也符合操作习惯。
- **同时出现场景**：他人弃牌可碰/吃（需上行过）+ 自己同回合有暗杠提示（本地过2），两组权限位同帧下发——这是唯一需要两个过并排的场景，也是 PRD 写「最右侧是过2」的原因。

### 代价与陷阱

- 枚举注释「过 1/过 2」按位序编号（1<<0、1<<1），与按钮名口径正好相反，读代码极易写反（见上文命名陷阱）。
- 「过2」是开发期「第二个过按钮」（KW_BTN_Guo2）命名直接透传到 PRD，未按语义命名（如「本地过」），可读性差。
- 客户端需自行维护过2 后按禁手重新压暗的一致性逻辑，漏做会出现「按钮收了但灰态错」的不同步表现。
