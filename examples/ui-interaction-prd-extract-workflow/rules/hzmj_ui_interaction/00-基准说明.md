## 二、基准性质

1. 本文档记录的是客户端**已实现的 UI 交互事实**，不是理想产品方案，也不是代码质量评价。它的用途是作为检查需求文档的标尺：需求文档写到的地方，逐条对照「界面区域、变化、条件、边界」是否定义、是否一致、是否完整。
2. 需求与基准冲突时，记为**需求的问题**，不因为实现如此就默认需求应改。基准描述的是现网行为，需求描述的是期望行为，两者地位不对等：先判定需求是否有明确依据，再判定冲突归因。
3. 需求明确有意不同、属于新需求改版的，记为 **P3 差异建议**，并在报告中提示需求补充「与现网实现的差异说明」，说明改动动机、影响范围与迁移或兼容策略。
4. 需求写明「本期不做」的项，不报缺失。只有需求声称要做、但没有写清交互事实的项，才进入缺失或不清判定。
5. 基准只覆盖客户端可观察的交互面。服务端协议字段、数值公式、匹配规则等非界面内容不在本基准范围内；规则中出现协议名，仅用于说明界面数据的来源与触发条件。

## 四、检查口径

### 4.1 单条规则的检查方式

每条规则按三段式 UI 事实陈述：**界面区域**（哪个界面的哪个节点或区域）、**变化**（显示 / 隐藏 / 置灰 / 文案 / 动画）、**条件**（触发消息、数据状态、房型、模式）。检查时对需求文档逐条回答三个问题：

1. 需求是否定义了该交互？（未定义且未声明本期不做，记 INCOMPLETE）
2. 需求的定义与基准是否一致？（区域、时机、条件、文案、互斥关系任一不符，记 CONFLICT）
3. 需求是否遗漏边界表现？重点是失败、超时、重连三类非常规路径。

### 4.2 交互限制四类重点维度

以下四类限制是检查重点，需求缺失即报 INCOMPLETE，不能以「正常路径写得通」为由放过：

| 维度 | 含义 | 典型检查点 |
|---|---|---|
| 前置守卫 | 操作或界面变化执行前必须满足的条件 | 未开局、已胡牌、非自己座位、非本房型、数据为空、模式为复盘 |
| 互斥 | 同一时刻只能存在一种状态或一个操作入口 | 操作区页面互斥、按钮组合互斥、弹层互斥、托管与手动操作互斥 |
| 超时 | 时间相关的自动推进或失效 | 倒计时归零、提示自动消失、等待面板循环、超时引导、超时后托管 |
| 失败与恢复 | 请求失败、断线、异常数据后的界面表现 | 发包失败无提示、服务端拒绝提示、重连场景恢复、结算兜底、重置清理 |

### 4.3 死代码与无消费方的处理

规则中标注「死代码 / 无消费方 / 无派发方 / 恒隐藏 / 恒为某值」的条款，只用于说明代码痕迹，**不作为要求需求覆盖的依据**：

- 需求未描述这些行为，不报缺失。
- 需求若描述了这些行为，且与实现不符（例如需求要求存在某个按钮、某条提示、某种置灰效果，而现网对应入口不可达），记 CONFLICT，并在报告中引用对应条款编号说明现网实际表现。
- 需求若把这类行为当作既有能力进行延伸设计，按「与现网实现的差异说明」处理，提示需求补充可达入口与触发条件。

### 4.4 结论分级

| 级别 | 适用情形 |
|---|---|
| INCOMPLETE | 需求缺少必要交互定义，或缺少前置守卫 / 互斥 / 超时 / 失败与恢复中的任一边界 |
| CONFLICT | 需求定义与基准事实不一致，或需求描述了现网不可达的行为 |
| P3 差异建议 | 需求有意改版，与现网实现不同但方向明确；建议补充差异说明，不判为错误 |

## 五、阅读与引用约定

1. 锚点格式统一为「文件 → 方法」。以 `42319/` 开头的锚点相对 `input-ui/xuanwulobby/assets/42319/`；以 `common_game/`、`node_modules/` 开头的锚点相对 `input-ui/xuanwulobby/assets/`。
2. 规则条款用「文件号#条款号」引用，例如 `01#36` 表示 01 号文件第 36 条，`04#64` 表示 04 号文件第 64 条。跨文件引用时使用该格式，避免条款号歧义。
3. 各文件开头均有范围说明，明确本文件收录与不收录的内容，跨文件主题以范围说明为准，不重复计数。
4. 条款编号在同一文件内连续，新增或调整条款时同步更新本文件的合计条数。
5. 规则正文只陈述事实与锚点，检查结论、问题分级与修复建议写在检查报告中，不回写规则文件。
