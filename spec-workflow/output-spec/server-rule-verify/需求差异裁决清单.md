## 条目一：AT-ST-C02-008 财神打出后按普通白板留在牌河

**需求原文**：财神打出后按普通白板的形态留在牌河，不再作为财神参与后续牌局。

**双栏对照**：

| 需求拆句 | 实现表现 | 结论 |
|---|---|---|
| 前半句：打出后**按普通白板形态**留在牌河 | 客户端：牌河与出牌放大牌面都会重新刷财神红，打出的白板财神仍被高亮标识为财神（出牌区列表 `BoxHzmjMah2DView.ts:1127-1132`；出牌放大 `BoxHzmjMainView.ts:1044-1054`）——已观察 UI 表现，作用域恒为 active | **冲突**（视觉冲突独立成立） |
| 后半句：**不再作为财神参与后续牌局** | 服务端：财神注册后即从吃碰杠候选组移除实际财神，打出的财神不再参与吃碰杠（`common_game/com_game/common_game_com_ju.cpp:248`，BoxJokerStep::Execute；翻财神时白板登记为替代牌） | 一致（受 cai_shen_type 配置影响：创房默认白板财神 0，玩家可选翻财神，RuleHzmj.ts:27/265-275 → 判 conditional） |

**复核结论**：服务端规则与后半句方向一致，但前半句的客户端视觉冲突不因服务端规则正确而消除（复核规则 `ui-conflict-stands-alone`）→ 差异维持 **conflict**，L7 判 **decision_required**，转人工裁决。

**裁决问题**（牌河财神高亮的表现口径）：





- [ ] A. 改客户端：打出的财神在牌河/出牌放大处按普通白板显示，去除财神高亮（以需求为准）
- [x] B. 改需求：接受打出的财神保持财神高亮（便于玩家追踪财神去向，以现状实现为准）
- [ ] C. 其他：\_\_\_\_\_\_\_\_\_\_（请备注期望行为）

**裁决**：☑ approved（**已裁决 B 改需求**：接受打出的财神保持财神高亮，便于玩家追踪财神去向；差异维持 conflict，需求侧修订待上游；reviewStatus 已落 approved，2026-11-14）

## 条目三：AT-ST-C10-021 补进的牌仍在禁张内不能打

**需求原文**：补进（杠后补牌等）的牌如果仍在禁张内，则不能打出。

**双栏对照**：

| 需求拆句 | 实现表现 | 结论 |
|---|---|---|
| 补进的牌仍在禁张内时不能打出 | 服务端：禁打判定 `Algorithm::IsLimitMah`（mah_frame/base/algorithm.cpp:380-388）按 is_danfang 二选一——单放牌只比 `play_limit.dfs`、手牌比 hands；补进牌（杠后补牌 TakeAfterKong、摸牌 CheckTake，com_take.cpp:19/45-46/72-74）走单放路径只比 dfs，而杭州麻将全部 play_limit 写入只填 hands（吃碰杠 common_game/com_game/common_game_com_action.cpp:151-1xx）→ 禁打名单对补进牌**数据上永不命中**（规则路径存在但好友房数据上不可达） | inactive（不可达） |

**复核结论**：服务端实现了禁打能力，但好友房配置数据下该规则对补进牌不可达（`common-capability-is-not-enabled` 同源逻辑）→ 作用域判 **inactive**，L7 判 **not_applicable**；基线差异维持 unverified（无升级建议），转人工确认口径。

- [ ] B. 接受现状：补进牌不受禁打名单约束（禁张只约束吃牌相关行为；需求侧修订或接受 inactive/not_applicable 口径）
